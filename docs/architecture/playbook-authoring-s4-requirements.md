## Требования и флаги

| # | Требование | Флаг | Почему (источник) |
|---|---|---|---|
| R1 | Hermes (`AUTHORING_PROMPT`) получает реестр проверок (ключи `createDefaultRegistry()` + однострочное описание) и каталог `library/step-types.json` (id — назначение); правило «programmatic = только ключи реестра, без инструкций» | 🟢 | Промпт-текст, аддитивно, локально. Источник: задача D1; ограничение — реестр и каталог уже существуют |
| R2 | Новая проверка на draft/edit/save: каждый ключ `validation` в шаге `execution_kind:"programmatic"` ∈ реестр; иначе repair с текстом ошибки | 🟡 | Новый контракт авторства, но только в authoring-пути (не в `_load`), agent-шаги не затронуты. Источник: задача D1 + ограничение `validatePlaybook` в `_load` |
| R3 | Новая проверка: `{var}` в `goal_template` кроме `{input}` должен быть объявлен в `inputs[]`; иначе repair (`{name} в goal_template без inputs[]`) | 🟡 | Затрагивает контракт подстановки (`playbook-store.substitute`); enforcement только на авторстве, `{input}` исключён. | R5 | Сводка черновика юзеру: шаги, реальные проверки, строка «когда использовать» | ⚪ | Только текст/UX, поведение системы не меняется |
| R6 | `save` повторяет те же проверки; при нарушении `ok:false` с конкретным ключом/переменной, файл профиля не пишется | 🟢 | Локально, один путь. Источник: задача D1 (защита от ручной правки черновика) |
| R7 | `edit` — тот же промпт и проверки; `when_to_use` сохраняется/обновляется | 🟢 | Локально. Источник: задача D1 |

Источник: задача D2; прецедент `buildDevPlaybookSuggestion` |
| R9 | Обычная просьба, совпавшая по смыслу с `when_to_use`, → агент предлагает/запускает плейбук без id от юзера | 🟢 | Поведение следует из блока промпта, нового контракта нет. Источник: задача D2 |
| R10 | `playbook_health`: профильный плейбук с непустым `when_to_use` → `dispatch: pass` (новый маршрут P); без — `fail` + подсказка «заполни when_to_use» | 🟢 | Локально в reachability. Источник: задача D2 + `checkPlaybookReachability` знает `pb.source==='profile'` |

## Неявные требования / ограничения (источник — другая часть системы)

| # | Требование | Флаг | Почему |
|---|---|---|---|
| C1 | Правила R2/R3/R4 живут в authoring-функции, НЕ в `validatePlaybook` (который зовётся в `_load`) | 🟢 | Иначе сломается загрузка уже сохранённых плейбуков у всех. Реальное ограничение кода |
| C2 | Обратная совместимость: существующие профильные плейбуки без `when_to_use` читаются/запускаются как раньше, в промпт не попадают, health подсказывает | 🟢 | Поле опционально для чтения/запуска; источник — требование не ломать прод |
| C3 | Промпт Hermes и блок промпта строятся из реестра/файла динамически, не хардкодом | 🟢 | Реестр и step-types пополняются, source of truth один |
| C4 | В agent-шагах `validation` любые ключи (LLM-судья), строгость только для programmatic | 🟢 | Так работают все системные плейбуки. Реальное ограничение |
| C5 | `instructions` в programmatic-шаге: правило промпта, не отказ на save | 🟢 | Разрешает открытый вопрос дизайна №1 карты |
| C6 | Точка инъекции блока — системный промпт профиля (не baseContext) | 🟢 | Разрешает открытый вопрос №2; задача прямо говорит «системный промпт» |
| C7 | `{input}` разрешён без объявления в `inputs[]` | 🟢 | Крайний случай сценария |
| C8 | Не-цели: runtime-разворачивание `{use: step-type}`, новые валидаторы, блоки S1–S3, lifecycle S5, маршруты системных плейбуков | 🟢 | Явно вне среза; иначе мультиплицирует объём |
| C9 | Нет миграции данных, новых прав/аутентификации/биллинга/мульти-тенантности | ⚪ | Изменения аддитивны, доступ не меняется |

## Челлендж 🟡 (не 🔴: права/безопасность/биллинг/необратимость/мульти-тенантность не затронуты)

**R2 (строгий реестр для programmatic).** Новые состояния: repair-круг на каждый невалидный черновик.
Типовой баг — ложный отказ у системных плейбуков, если правило протечёт на agent-шаги или в `_load`.
Цена мала: правило узкое (programmatic + authoring). Дешёвая альтернатива «только промпт, без проверки» —
отвергнута: именно так `shell_command_success` просочился в сохранённый черновик (D1).

**R3 (`{var}` без `inputs[]`).** Новые состояния: draft/edit/save × необъявленная переменная.
Риск — блокировка правки старых плейбуков, но это ровно дефект из живого примера (литерал `{scenario}` в цели плана).
`{input}` исключён. Дешёвая альтернатива «предупреждать» — отвергнута: битый литерал ломает план молча.

**R4 (`when_to_use` в схеме).** Схему читают сиблинги в `.core`/CI. Безопасна ТОЛЬКО как добавление
опционального поля; удаление/переименование было бы 🔴. Новых состояний нет. Альтернатива «хранить вне схемы» —
отвергнута: нужна и для блока промпта, и для health.

**R8 (инъекция в системный промпт).** Сквозное влияние на каждую сессию профиля, риск роста контекста.
Новые состояния: 0 / 1..10 / >10 плейбуков; профили с internalGtd. Типичный баг — неограниченный рост промпта
и кросс-влияние с dev-подсказкой. Митигации: лимит ≈10 × ~160 симв., явное «ещё N», только `scope:profile`,
пропуск internalGtd. Дешёвая альтернатива «не инъектить, ждать id от юзера» — отвергнута: это и есть D2.

## Принятые решения по неоднозначностям (⚫ не остаётся)
- Инструкции в programmatic-шаге: запрещаем в промпте, на save не отклоняем (C5) — вопрос закрыт.
- Точка инъекции: системный промпт профиля (C6) — вопрос закрыт.
- `when_to_use` при редактировании старого плейбука без поля: любой save профильного плейбука требует непустой
  `when_to_use` → repair. Старые файлы при этом читаются/запускаются без изменений (C2). Цена — один repair-круг.

## Отвергнуто (если кто-то вернёт — это 🔴)
- Программная проверка исполнения команд (`shell_command_success` / `http_ok_contains_sha`): новые полномочия
  исполнения, отдельное решение по безопасности, вне S4a/S4b (не-цель сценария).

## Итог
🔴 и ⚫ среди требований нет → подтверждения пользователя на этом шаге не требуется.
Минимальный набор: R1–R10 + C1–C9. Жёлтых четыре (R2, R3, R4, R8), все с дешёвой митигацией и обоснованием.
