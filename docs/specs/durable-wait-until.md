# Durable wait («уснуть до условия») для шагов durable-плана

**Зачем.** Инженерный процесс постоянно чего-то ждёт: CI, мерж, деплой, креды
от пользователя, повтор ошибки в логах, другой план, ответ пользователя через
3 дня, просто «понаблюдать сутки». До этого programmatic-шаг, который ещё не
готов, считался **провалом**: 3 попытки с грейсом 30 с — и шаг умирал через
~1.5 мин. Агент-шаг мог только ждать внутри рана (жжёт модель, упирается в
таймаут) или провалиться.

**Индустриальный аналог.** Temporal: `await condition` / durable timer / signal;
AWS Step Functions: Wait state + callback task token. У нас — колонка
`task_items.wait_json`, которую опрашивает уже существующий 5-минутный GTD-тик.

## Два входа, одна модель состояния (`src/durable-wait.js`)

| Вход | Условие | Что после |
|------|---------|-----------|
| Плейбук: programmatic-шаг с `wait: {poll_every_sec, timeout_sec}` | собственная `validation` шага | pass → шаг завершается (`then: complete`); таймаут → обычный путь провала (recovery, затем `on_fail`/`task_failed` хуки) |
| Агент в середине шага: MCP `task_item_wait` + финальная строка `DURABLE: waiting` | `until` (любые детерминированные валидаторы), `awaiting_user`, `sleep_sec` | условие/побудка/таймаут → **тот же шаг перезапускается** с блоком `[ПРОБУЖДЕНИЕ ПОСЛЕ ОЖИДАНИЯ]` (что ждали, что произошло, evidence или ответ пользователя) |

Инварианты (`test/durable-wait.test.cjs`):

- опрос **не** создаёт execution и **не** тратит попытку; ран, запросивший
  ожидание, попытку возвращает (`parkItem refundAttempt`);
- опрос только детерминированный — LLM-судью «зелёный ли CI» не спрашиваем;
- ждущий шаг блокирует следующие шаги плана (позиционный гейт `claimNextRunnable`);
- `until` с неизвестным валидатором отклоняется сразу (MCP и компилятор), а не
  спит до таймаута; `wait` в плейбуке разрешён только на programmatic-шаге;
- финальный провал (`evidence.final`, например CI завершился красным) будит шаг
  сразу — ждать до таймаута бессмысленно; агент видит failing-чеки и чинит;
- `DURABLE: waiting` без зарегистрированного ожидания — ограниченный провал, не
  тихая парковка;
- рестарт процесса не теряет ожидание: всё в SQLite, тик сам продолжит.

## Ответ пользователя

`awaiting_user: true` — ничего не опрашивается, шаг спит до дедлайна. В каждый
обычный чат-ран профиля инжектится `[ПЛАНЫ ЖДУТ ОТВЕТА ПОЛЬЗОВАТЕЛЯ]`
(`buildAwaitingUserNotice`) — если сообщение отвечает на вопрос, агент зовёт
`task_item_wake(item_id, message)`, и план продолжается с этим ответом.
Для кредов проще `until: {credential_present: "<service>"}` — будится сам.

## Валидаторы для ожиданий

Существующие: `ci_green`, `merged`, `pr_opened`, `command_exit_zero`,
`file_exists`. Новые: `credential_present` (`~/agent-tokens/<profile>/<service>`),
`http_ok` (`{url, contains}` — например `/health` содержит SHA деплоя),
`task_done` (другой durable-план профиля завершён). Логи —
`command_exit_zero` с `journalctl … | grep -q …`.

PR для `ci_green`/`merged` ищется: явное значение (`{"ci_green": "<PR url>"}`) →
текст шага → **evidence предыдущих шагов плана** (последняя ссылка) → цель.
Так «Wait for CI» находит PR, который напечатал шаг «Open PR».
