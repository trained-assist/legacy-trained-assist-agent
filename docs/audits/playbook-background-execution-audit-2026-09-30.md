`debugging`, `new-software`, …) в фоне: эффективность, правильность процесса,
трата токенов, вылетевшие баги. Материал — живая прод-данные, а не дизайн-доки.

## 3. Эффективность: что показали цифры

### 3.1 Доля провалов

| opencode | 431 | 186 | **43%** |
| claude | 68 | 8 | 12% |

Средняя длительность **провального** рана opencode — **402 с**, успешного — 362 с.
Провал стоит почти столько же, сколько успех, и вдобавок порождает ретрай.

**Сожженное время:** 186 failed × ~402 с + 40 interrupted × ~399 с ≈ **25 часов**
агентного wall-clock впустую. 40 interrupted — срезы рестартами (32 из них за один
день 27.09, пока шли деплои).

### 3.2 Главный источник провалов — хрупкий `DURABLE:`-протокол

Из 186 провалов opencode **174 (94%) — `no DURABLE terminal marker in reply`**
(`src/gtd-controller.js:816`). Разбивка по контракту шага:

| level / role | провалов «no marker» |
|---|---|
| master / developer | 52 |
| bachelor / verifier | 34 |
| bachelor / researcher | 23 |
| bachelor / developer | 22 |
| master / researcher | 18 |
| остальные | 25 |

Это **не качественные** провалы, а протокольные: агент часто реально сделал шаг,
но не дописал финальную строку. Пример из evidence шага `bf92e9dc` (план
`3e40a139`, шаг «Архивация»): в ответе полный итог со ссылками на PR #68 и
issue #51, работа сделана, — но финальной строки `DURABLE: done` нет → попытка
списана, запущен ретрай с причинами, затем эскалация уровня.

Только в выборке из 30 последних «no marker»-провалов **27 stored-reply
содержали осмысленную работу** (не пустой ответ).

**Следствие — дорогие эскалации.** Классическая цепочка recovery
(`src/durable-recovery.js`): попытка 1 на том же уровне → попытка 2 с причинами
провала во входе → попытка 3 на **следующем уровне**. В итоге:

- **66 эскалаций** `bachelor→doctor` (34) и `master→doctor` (32) — переход с
  opencode/deepseek на **claude** из-за того, что модель не дописала маркер;
- 82 doctor-рана суммарно, из них 12 снова провалены;
- **70 шагов** съели все 3 попытки, **32 шага** — по 2; рекордсмен — шаг
  «Исследование…» с **14 попытками** (план `849669d6`), второй — 7 попыток.

Оценка токенов по выборке `usage.json` (log обрезан до 500 последних записей):
durable-раны (240 записей) ≈ 20.8M input + **308M cache_read** + 1.25M output.
Среднее на ран: ~87k input и **~1.28M cache_read** токенов. Умножение на
бесплодные ретраи и doctor-эскалации — основная нерациональная статья расхода.

### 3.3 Простой планов — позиционный гейт + молчаливые ожидания

`claimNextRunnable` пропускает шаг, только когда **все предыдущие** `done|skipped`
(`src/durable-task-store.js:481`). Один `waiting`/`failed` шаг блокирует весь хвост:

- **285 pending** шагов при 14 waiting + 8 failed — почти весь backlog стоит
  за заблокированными головами;
- типичная картина активного плана: `done=10, wait=1, fail=1, pend=4` — четыре
  шага не двигаются из-за одного;
- планы висят `active` **21–46 часов** (max — пакет выставок `8e1fba92`, 46.4 ч).

Отдельно: **6 шагов в `awaiting_user`** (ждут владельца: Weeek-токен, выбор
цели, ответ в боте) — стоят сутки-трое, и никто об этом не знает (см. §4.2),
и ещё **7 шагов спят в «Наблюдение после релиза сутки»** (`timeout_sec` до 172800),
формально держа планы `active` ещё сутки после фактического завершения.

Итог по wait-событиям: 14 активных ожиданий, из них 6 — `awaiting_user`.

### 3.4 Programmatic-шаги: таймаут «PR смержен» и падение валидаторов

8 `failed` шагов, из них **3 — «PR смержен»** с evidence
`{"state":"closed","merged_at":null}` или `{"state":"open"}` (планы `61ac1e86`,

Сегодняшняя (30.09) цепочка из журнала:

Три рана programmatic-шага впустую за 9 минут — потому что класс ошибки
`UNKNOWN` не даёт recovery-политике ничего умного.

## 4. Вылетевшие баги и дыры процесса

### 4.1 Сбой движка превращается в «провал по качеству» (не заведён отдельно)

Раннер, вернув текст-ошибку («⚠️ Процесс завершился с ошибкой (код 1)»,
«⛔ Вся лестница моделей … недоступна», «llm-ladder недоступен»), отдаёт его
как **обычный ответ шага**. `settleDurableReply` не находит маркер → ветка
`no terminal marker` → `recoverDurableItem(..., quality: true)` → ретрай, а затем
**эскалация до doctor**. Сбой инфраструктуры сжигает попытки и переводит шаг на
дорогую модель. Упомянуто в #1703 как «чинить отдельно» — **отдельного issue нет**.

Доказательства в `task_items.last_error`:
- `no DURABLE terminal marker in reply: ⚠️ OpenCode завершился с ошибкой: every rung failed` — **25 штук**;
- `… ⛔ Сервис моделей llm-ladder недоступен (лестница «deepseek»)…` — 5;
- `… ⛔ Вся лестница моделей «deepseek» временно недоступна …` — 4.

Плюс за 2 дня в журнале **397 записей `llm-ladder HTTP 502: every rung failed`**
(таймауты opencode-go ступеней + `HTTP 402` на платной хвостовой ступени) —
внешняя лестница была недоступна массово, и каждый такой сбой попадал в планы
как quality-fail.

### 4.2 Уведомления владельцу не работают: 52 из 63 хуков скипнуты

```
hook_executions: notify fired=11, skipped=52
причина скипа (все 52): "no explicit consent for notify"
```

Плейбуки объявляют `hooks.task_done / task_failed / on_fail → notify owner`,
но исполнение требует **явного согласия, которого никто не давал**. Практический
итог:

- провал шага и вопрос `awaiting_user` **не доходят до владельца** (если только
  не сработал встроенный `buildAwaitingUserNotice` в обычном чат-ране);
- «план готов» тоже не приходит в 52 случаях из 63;
- владельцы узнают о застрявших планах, только когда сами заглянут.

Упомянуто в #1703 («только Telegram и только при привязанном чате»), но корень
шире: **consent-гейт не имеет способа дать согласие**.

### 4.3 Таймаут шага не классифицируется

`execution_timeout_seconds` (дефолт 600 с) убивает движок, но:

- **103 завершённых рана длились >10 мин** (максимум 2620 с ≈ 43 мин — кламп
  `execution_timeout` ≤ 40 мин);
- при этом **0 executions** с `error_text`, содержащим `timeout`/`timed out`/`killed`.

То есть убитый по таймауту шаг оформляется как обычный безмаркерный провал →
`UNKNOWN` → conservative_retry/fallback/эскалация. Отдельного класса `TIMEOUT`
нет ни в строках executions, ни в recovery-политике.

### 4.4 Атрибуция исполнений пуста — токены неоптимизируемы

Во **всех 622 executions**: `model=NULL`, `attempt_number=NULL`, `result_json=NULL`.
При этом колонки существуют (миграция `durable-task-migrations.js`).
Следствия:

- нельзя ответить «сколько токенов сожрал шаг X на модели Y»;
- нельзя связать провал с конкретной моделью лестницы (какая ступень отказала);
- `usage.json` ведёт только суммарные счётчики профиля, а его `log` **обрезан
  500 записями** — историческая аналитика невозможна;
- `executions.provider` почти всегда NULL (1 запись `fallback-from-opencode`).

## 5. Что работает хорошо

- **Детерминированные wait-валидаторы** (`ci_green`, `merged`, `file_exists`,
  `command_exit_zero`, `http_ok`) — опрос без LLM, без траты попыток, ран
  возвращается при `refundAttempt`. Это лучшая часть системы.
- **Resume после рестарта** (#1671/#1674): pending-journal + `resumeSink` +
  native `--session` resume — interrupted-шаги возвращаются в очередь.
- **Один workspace и одна сессия на план** (#1647/#1684) — файлы шагов видны
  следующим шагам, контекст не смешивается между планами.
- **Digest предыдущих шагов** (`priorStepsDigest`, ≤7000 симв.) — каждый ран
  дёшев по входу: промпт шага компактен, история не тащится целиком.
- **Бесплатная лестница**: 619/622 ранов на `tier=free`; деньги тратятся
  в основном только на doctor-эскалации (которые, как показано, чаще
  бесполезны).
- **Defects-журнал и `GET /internal/e2e/defects`** — мягкие проходы не теряются.
- **Оперативное починение**: за 27–29.09 закрыты #1627, #1628, #1637, #1647,
  #1657, #1662, #1674, #1677, #1678, #1683, #1684, #1697 — процесс самоисцеления
  через e2e-тред #1642 работает.

## 6. Рекомендации (по приоритету)

### P0 — остановить сжигание попыток

1. **Переживать отсутствие `DURABLE:`-маркера** (#1907). Если маркера нет, но ответ
   содержит `ИТОГ ШАГА` / делает видимый результат — считать это кандидатом на
   «сделано» и прогонять через судью (один дешёвый вызов `serviceLlm`), а не
   списывать попытку и не эскалировать. Порог: 94% провалов opencode и 66
   дорогих эскалаций — цена одного регэкспа.
2. **Сбой движка → класс TRANSIENT, не quality** (#1908). Для `internalGtd`-ранов раннер
   должен отдавать краш/`every rung failed`/502 как reject с классом
   `MODEL_ERROR|TRANSIENT`; recovery — backoff и повтор на том же уровне,
   без эскалации. (Из #1703.)

### P1 — видимость и атрибуция

3. **Согласие на `notify`** (#1909). Способ дать consent (флаг профиля или первая
   настройка), либо дефолт для владельца-одиночки; иначе `awaiting_user` и
   провалы остаются невидимыми, а планы стоят сутками (52/63 скипа).
4. **Писать `model`, `attempt_number`, `result_json` (в т.ч. usage) в
   executions** (#1910) — без этого любая оптимизация токенов слепа. Плюс подумать над
   ретенцией `usage.json` log (>500 записей) или отдельной durable-таблицей.
5. **Класс `TIMEOUT`** (#1911): kill по `execution_timeout_seconds` должен оформляться
   как timeout (свой класс recovery: backoff + possibly escalate timeout, а не
   «агент ответил плохо»).

### P2 — гигиена процесса

6. **Алерт на деградацию лестницы** (#1912): N подряд `every rung failed` → уведомление
   оператору (сейчас 397 записей за 2 дня никто не заметил в моменте).
7. **Убрать no-op'ы и дрейф доков** (#1913): `context_budget`, no-op эскалация
   bachelor→master, `docs/playbooks.md` (карта audience → `feature`, отсутствие
   плейбука `development`), `DEFAULT_LEVEL_MAP` против user-scenario-дока,
   роль-игнорирование opencode, локальная копия `doctor`-лестницы.

## 7. Итог

Процесс **архитектурно зрелый** (durable-состояние, resume, детерминированные
валидаторы, defects-журнал) и уже доказал сквозной прогон. Но три вещи делают
его дорогим и молчаливым:

1. **хрупкий строковый протокол `DURABLE:`** — 94% провалов opencode и 66
   эскалаций на Claude, которые были не нужны;
2. **молчаливые хуки** — владелец не видит застрявших шагов, планы простаивают;
3. **слепая атрибуция** — `model`/`attempt_number`/`usage` не пишутся, поэтому
   даже найденная экономия не измеряется.

Исправления P0–P1 закрывают все три и, по оценке среза, убирают большую часть
из ~25 ч/нед сожженного агентного времени и соответствующего расхода токенов.
