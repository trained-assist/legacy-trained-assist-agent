# Core 05 — Ожидание событий durable-плана (GitHub-вебхук поверх 30-с опроса)

**Эпик:** [#1846](https://github.com/trained-assist/trained-assist-agent/issues/1846)
**Область:** механизм ожиданий шагов durable-плана (`src/durable-wait.js`,
реестр `src/playbook-validators.js`, вебхук `POST /webhooks/github`).
**Доменные потребители:** инженерные плейбуки (`development`, `feature`), любой
плейбук/бот, чей шаг ждёт PR, CI или прогон GitHub Actions.

---

## Ценность

**Исполнитель шага плана просыпается через секунды после того, как GitHub-событие
(смерженный PR, зелёный CI, завершённый прогон) реально произошло, — план доезжает
до конца без ожидания следующего тика и без ручного толчка владельцу.**

Актор — агент-исполнитель шага durable-плана (выгодоприобретатель — владелец плана:
короче цикл, меньше жжёных сессий).

**Доказанность: V2** — голосовой запрос владельца 29.09.2026 (эпик #1846, он же
пользователь плейбуков). Пол 5 мин уже снят планом «убрать 5-минутный пол»
(`a61bb2c5`, PR #1865: лёгкий 30-с тик ожиданий + мгновенный wake на ответ
пользователя/креды), но для CI/мержа остаётся опрос: событие GitHub не разбудит
шаг быстрее `poll_every_sec`. Уровень не блокирует работу.

---

## Контекст (что есть сегодня)

- Шаг может спать: `task_item_wait(until: {<валидатор>: <субъект>})` + финальная
  строка `DURABLE: waiting`; состояние — колонка `task_items.wait_json` (SQLite).
- Просыпает сейчас лёгкий тик ожиданий (шаг ~30 с, `MIN_POLL_SEC=30`) и мгновенный
  `POST /internal/durable/kick` для ответа пользователя/кредов — детерминированные
  валидаторы, без LLM.
- Реестр проверок (`createDefaultRegistry`): `ci_green`, `ci_run_green`,
  `merged`/`pr_merged`, `pr_opened`, `http_ok`, `task_done`, `command_exit_zero`,
  `file_exists`, `credential_present`, `fanout_joined`… — это и есть зародыш
  каталога событий.
- Вебхуков GitHub в агенте нет; единственный `/webhooks/*` — weeek-session.
- Публичный адрес агента есть (`AGENT_PUBLIC_URL`), т.е. точка входа для GitHub достижима.

## Сценарий

### Фаза 0 — Однократная настройка (ops, не каждый запуск)

**0.1** Вебхук на орг `trained-assist` (наши репо): Settings → Webhooks →
`POST <AGENT_PUBLIC_URL>/webhooks/github`, секрет, события `pull_request`,
`workflow_run`, `workflow_job`, `check_suite`, `issues`.

- **КОГДА** пришёл запрос с неверной/отсутствующей подписью `X-Hub-Signature-256`
  (HMAC-SHA256 от тела запроса секретом) **ТОГДА** агент отвечает 4xx и не трогает
  ни один шаг — payload никогда не является вердиктом.
- **КОГДА** вебхук не настроен вовсе **ТОГДА** фича деградирует ровно до сегодняшнего
  поведения: опрос тиком, шаги просыпаются не позже интервала.

### Фаза A — Шаг подписывается на событие

**A.1** Шаг N плана заканчивается результатом (PR URL, номер issue, id прогона) и
попадает в дайджест `[ИТОГИ ПРЕДЫДУЩИХ ШАГОВ ПЛАНА]` для шага N+1.

- **КОГДА** следующему шагу нужно ждать внешнее событие **ТОГДА** агент вызывает
  `task_item_wait(item_id, until: {"issue_pr_merged": "trained-assist/repo#1846"})`
  (или `issue_pr_ci_green`, `workflow_run_completed: "<…>/actions/runs/<id>"`,
  `workflow_job_completed`, `merged`, `ci_green`, …) и завершает ран строкой
  `DURABLE: waiting`.
- **КОГДА** в `until` назван неизвестный тип **ТОГДА** тул отклоняет запрос сразу,
  перечислив каталог событий, — шаг не спит до таймаута с заведомо невыполнимым
  условием.
- **КОГДА** ожидание зарегистрировано **ТОГДА** item переходит в `waiting`
  (`wait_json`: `until`, `deadline_at`, `poll_every_sec`), позиционный гейт
  `claimNextRunnable` держит последующие шаги, попытка (`attempt_count`) не тратится.

**A.2** Описание MCP-тула `task_item_wait` и этот сценарий содержат каталог:
тип события, формат субъекта, пример вызова. (Спецификация
`docs/specs/durable-wait-until.md` удалена чисткой docs/specs (#1847) — живое
описание каталога держим в описании тула и здесь.)

### Фаза B — Мгновенная доставка (fast path)

**B.1** GitHub доставляет событие на `POST /webhooks/github`.

- **КОГДА** подпись HMAC верна **ТОГДА** сервер по типу события находит ждущие шаги
  с совпавшим субъектом (матчер: тип + `owner/repo#n` / URL рана) и подаёт им **kick**
  — один будильник на событие, дубли идут в никуда (идемпотентно).
- **КОГДА** подошёл kick **ТОГДА** проверку выполняет тот же детерминированный
  проверщик из реестра (`issue_pr_merged`, `workflow_run_green`, …): вебхук будит,
  но не решает.

**B.2** Вердикт проверщика:

- **КОГДА** проверщик подтвердил условие **ТОГДА** шаг разблокируется с блоком
  `[ПРОБУЖДЕНИЕ ПОСЛЕ ОЖИДАНИЯ]` (что ждали, что пришло, evidence) и завершается
  штатно.
- **КОГДА** проверщик не подтвердил (ложное срабатывание, чужой PR по той же
  issue, ещё красные чеки) **ТОГДА** шаг остаётся `waiting` и продолжает ждать —
  следующий тик по опросу.
- **КОГДА** событие означает финальный провал (`evidence.final`: CI завершился
  красным, PR закрыт без мержа) **ТОГДА** шаг будится сразу и уходит по ветке
  провала (агент видит failing-чеки и чинит / `failed`), не дожидаясь таймаута.

**B.3** Запасной путь (всегда):

- **КОГДА** вебхук не пришёл (настроен только опрос, потерян, чужое репо
  пользователя) **ТОГДА** тик ожиданий опрашивает проверщик с `poll_every_sec` —
  шаг просыпается не позже интервала. Потеря вебхука = медленнее, но не сломаннее.

### Фаза C — Продолжение плана

- **КОГДА** ждущий шаг завершён **ТОГДА** следующий по позиции шаг claim-ится сам,
  владелец видит прогресс в `checklist.md`.
- **КОГДА** истёк `deadline_at` **ТОГДА** `expireWaitingDeadlines` переводит шаг в
  `failed`, а не в вечный `pending`.
- **КОГДА** процесс агента перезапущен во время ожидания **ТОГДА** ожидание
  переживает рестарт (всё в SQLite, тик продолжит с того же места).

### Фаза D — Потребление плейбуком `feature`

- **КОГДА** плейбук ставит шаг «CI зелёный» / «PR смержен» **ТОГДА** он объявляет
  `wait`/`until` через событие каталога, а не sleep-цикл внутри рана — так уже
  сделано (`until: {ci_green: "<PR url>"}`, programmatic `wait` с `validation: merged`);
  `delay_after_sec: 600` из таблицы #1611 на main больше нет.
- **КОГДА** у шага нет ссылки на PR, а есть только issue или id прогона **ТОГДА**
  плейбук подписывает его на тип каталога с этим субъектом
  (`issue_pr_merged: "owner/repo#N"`, `workflow_run_completed: "owner/repo/actions/runs/<id>"`).

## Не-цели

- Универсальная шина событий для не-GitHub источников (каталог архитектурно
  открывает тип = проверщик + опциональный матчинг вебхука — но не сейчас).
- GitHub App для чужих репо пользователей: для них остаётся опрос (отдельный заход).
- Превращение payload вебхука в источник истины (только kick проверки).
- `issue_created` / `issue_closed` — типы возможны в каталоге «по необходимости»;
  этот сценарий их не требует, в первый заход не завязываем.
- Переработка плейбука `development` и P4-хуков — остаются как есть.

## Крайние случаи

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Секрет/URL вебхука не настроен | 4xx на чужие запросы; ожидание работает через опрос |
| Событие пришло раньше подписки шага | матчер не находит ждущих → игнор, продолжает опрос |
| Субъект не совпал (чужой PR той же issue) | kick есть, проверщик отвечает «не готово» → шаг ждёт дальше |
| Пропущенное/задублированное событие | дубль не будит повторно; пропуск закрывает опрос |
| Токен/GitHub недоступен у проверщика | `inconclusive` → следующий опрос, не `failed` |
| Рестарт агента в середине ожидания | `wait_json` в SQLite, поведение не меняется |
| Ждём дольше `deadline_at` | `failed` с причиной, не бесконечное `waiting` |

## Проверка (см. эпик #1846)

1. Юнит на каждый новый проверщик (фейковый `ghFetch`) и на матчинг вебхука
   «событие → ждущий шаг».
2. Прод: шаг ждёт `workflow_run_completed` по реальному id прогона и просыпается
   < 1 мин после завершения (с вебхуком — секунды).
3. Отрицательный прогон: вебхук выключен → тот же шаг просыпается опросом
   (путь деградации).

## Открытые вопросы

Нет — формат событий, состав каталога, роль вебхука (kick, не вердикт) и запасной
путь опроса заданы в эпике #1846; решения по краевым случаям приняты выше.
