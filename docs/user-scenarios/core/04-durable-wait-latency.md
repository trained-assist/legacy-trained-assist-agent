# Core 04 — Ожидания шагов durable-плана без 5-минутного пола

План `a61bb2c5` (feature, 15 шагов) · требование владельца `[202]` из requirements-log
(голос 29.09 06:03: «5 минут ждать — это хрень») · PR [#1865](https://github.com/trained-assist/trained-assist-agent/pull/1865)
(merge `e29b953`, в проде) · дизайн и лог шагов — issue [#1850](https://github.com/trained-assist/trained-assist-agent/issues/1850)

Статус: **работает на main и проверено в проде.** Опрос ожиданий — раз в ~30 с
(пол опроса 30 с), ответ пользователя и появление кредов будят шаг сразу,
чек-листовый GTD-тик остался 5-минутным. Ниже — что именно есть сейчас.

## Зачем (было)

Механизм «шаг плана уснул до условия» работает и сейчас: `task_item_wait` на
programmatic-шаге, детерминированные валидаторы, рестарт не теряет ожидание
(состояние в SQLite).

Была дыра в **тайминге пробуждения**: всё, что ждёт, реально проверялось только на
глобальном GTD-тике (`setInterval(run, 5 * 60 * 1000)` в `src/server.js`
`scheduleGtdController` → `gtd.runDue` → `runDueDurable` → `pollDurableWait`).
`poll_every_sec` клампился от `MIN_POLL_SEC = 60` и фактически игнорировался —
интервал опроса был 5 минут. `task_item_wake` только писал `woken_at` в `wait_json`
и ждал следующего тика (MCP-тул живёт в отдельном процессе — `kickDurable()` из
его тела не зовётся напрямую). Цена: план выглядел зависшим — ответили юзеру или CI
уже зелёный, а следующий шаг не начинается до 5 минут.

## Ценность (V)

**Пользователь, чей план ждёт CI, мержа, деплоя или своего ответа, получает
продолжение шага в секунды–минуты после наступления условия — вместо молчания до
5 минут; план выглядит живым.**

Уровень **V3** — фича-реквест реального пользователя (владельца), задокументирован:
requirements-log `[202]` (Intensity 2) + голосовое 29.09 + задача плана `a61bb2c5`.
Внешних custdev-данных нет; для платформенной правки такого масштаба этого достаточно.

## Термины (как в коде)

- **GTD-тик** — глобальный проход `runDue` (5 мин, `src/server.js`
  `scheduleGtdController`): legacy-записи `gtd/*.json` (чек-листы, кроны) **и**
  полный проход durable-шагов. Не тронут этим планом.
- **Тик ожиданий** — лёгкий интервал ~30 с (`DURABLE_WAIT_TICK_MS`, дефолт
  `30_000`, `0` = выключить → деградация к 5-мин тику): опрашивает **только**
  ждущие durable-шаги детерминированными валидаторами, без LLM и без чек-листов.
  Первым идёт счётчик `countActiveWaits()` — при нуле выход без запросов.
- **Wake** — `task_item_wake` → `woken_at` в `wait_json` **+** немедленный кик.
- **Kick** — `kickDurable()` (`src/gtd-controller.js`), дебаунс 3 с, проход
  сериализован (`runDurableSerialized`). Внутри сервера — прямой вызов
  (`src/durable-kick.js` `useInProcess`); из другого процесса (MCP-тул, запись
  креды) — `POST /internal/durable/kick` c `AGENT_SECRET` (фолбэк
  `AGENT_RUN_TOKEN`). Ошибка кика проглатывается: деградация к тику ожиданий.
  Kill-switch: `DURABLE_KICK=0`.

## Не-цели (сознательно НЕ делаем)

- **Не ускоряем чек-листовый GTD-тик** — legacy `gtd/*.json`, кроны, ETA-доводка и
  `FIRE_LEASE_MS` остаются на 5 минутах. Ускорено только ожидание durable-шагов.
- **Не трогаем первый тик после старта** (2 мин) — он про чек-листы, не про ожидания.
- **Не строим свой event-bus вместо GitHub webhook** — событийный CI либо уже есть, либо уходит в follow-up issue #1846.
- **Не добавляем LLM в опрос** ожиданий: валидаторы только детерминированные, попытка на будильнике не тратится.
- **Не делаем drain / «рестарт запланирован» / рассылок** — рестарт мгновенный и тихий, ожидания переживают его в SQLite.
- **Не поднимаем второй процесс сервера** для опроса (ловушка: дублирует pending-tasks).

## Крайние случаи

- **Ждущих шагов нет** → тик ожиданий — no-op: счётчик `countActiveWaits()` → 0 → выход без выборки.
- **Спам пробуждений** (пользователь пишет подряд, условие мигает) → дебаунс 3 с + сериализация; лишний wake = «пересмотреть сейчас», попытка не тратится (DW-01).
- **Wake по невыполненному условию** → шаг снова уходит в `waiting`, блокировка следующих шагов сохраняется.
- **Кик не дошёл** (ошибка HTTP, нет секрета, `DURABLE_KICK=0`) → деградация к тику ожиданий (≤ ~60 с), внутри бюджета DW-05; событие не теряется.
- **Rate limit GitHub API**: один ждущий `ci_green` при 30 с ≈ 120 запросов/час (лимит токена 5000/час — запас есть). Если ждущих шагов станет много — общий интервал/backoff, это называется вслух, не прячется.
- **Проснувшийся шаг и очередь слотов** (#1752): он стартует только в свободный слот, как и сейчас, — ускорение пробуждения не увеличивает параллелизм.
- **Пустой/битый `until`** → отклоняется сразу (неизвестный валидатор), поведение сохранено.
- **SQLite занят** → наблюдение после релиза: `kick error: database is locked` 1 случай из 162 (≈0.6%) — страховка (тик ~30 с) отработала, задержка не потеряна, но событие не видно. Follow-up: #1965.

## Как проверяется

- Юниты: `test/durable-wait.test.cjs`, `test/durable-wait-tick.test.cjs` (зелёные в CI).
- Песочница одной командой: `npm run sandbox:durable-wait` → 9/9 PASS, ~0.6 с, exit-код (CI-гейт PR).
- Прод-смоук (S4/S6, профиль `iso-smoke`, боевой store): 4 плана, парковка 13.2/16.1 с; фактический опрос `poll_every_sec: 30` = 30.0 с; wake из отдельного процесса → проход сервера 3.23 с; условие → `done` 26.8 с и 30.1 с; `tickCount` 1 → 1 (будил тик ожиданий, не 5-мин чек-листовый). Логи, прогоны: issue #1850.
