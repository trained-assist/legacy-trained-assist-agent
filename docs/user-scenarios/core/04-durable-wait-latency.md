# Core 04 — Ожидания шагов durable-плана без 5-минутного пола

План `a61bb2c5` (feature, 15 шагов) · требование владельца `[202]` из requirements-log
(голос 29.09 06:03: «5 минут ждать — это хрень») · дизайн — issue #1850

Статус документа: **код сделан** — срезы S1–S5 в ветке плана (пол опроса 30 с,
тик ожиданий, будильник, доки выше); остаётся S6 = прод-приёмка «пробуждение
<1 мин» после мержа. Описание «что есть на main» ниже — состояние ДО этого плана.

## Зачем (что было на main до этого плана)

Механизм «шаг плана уснул до условия» **работает**: `task_item_wait` / `wait` на
programmatic-шаге, детерминированные валидаторы, рестарт не теряет ожидание
(описание MCP-тула `task_item_wait`, issue #1850).

Дыра — в **тайминге пробуждения**. Всё, что ждёт, реально проверяется только на
глобальном GTD-тике:

- `src/server.js` `scheduleGtdController`: первый тик через 2 мин, дальше
  `setInterval(run, 5 * 60 * 1000)` → `gtd.runDue` → `runDueDurable` → `pollDurableWait`
  (`src/gtd-controller.js:580`).
- `poll_every_sec` клампится от `MIN_POLL_SEC = 60` (`src/durable-wait.js:29`) и
  **фактически игнорируется**: интервал опроса = 5 минут, а не то, что указал исполнитель.
- `task_item_wake` (`src/mcp-skills/tools/101-durable-tasks.js:331`) только пишет
  `woken_at` в `wait_json`. Будильника нет, а MCP-тул живёт в отдельном процессе
  (`src/mcp-action.js` — каждый вызов свежий `mcp-skills/index.js`), поэтому
  `kickDurable()` из тела тула напрямую не позвать. Ответ пользователя ждёт до 5 минут.
- Вебхуков GitHub на CI нет (`workflow_run` не подключён) — «зелёный CI» тоже ждёт тик.

Цена для пользователя: план выглядит **зависшим** — он отвечает или CI уже зелёный,
а следующий шаг не начинается до 5 минут.

## Ценность (V)

**Пользователь, чей план ждёт CI, мержа, деплоя или своего ответа, получает
продолжение шага в секунды–минуты после наступления условия — вместо молчания до
5 минут; план выглядит живым.**

Уровень **V3** — фича-реквест реального пользователя (владелец), задокументирован:
requirements-log `[202]` (Intensity 2) + голосовое 29.09 + эта задача плейбука.
Внешних custdev-данных нет; для небольшой платформенной правки этого достаточно,
но незадокументированного спроса не предполагаем.

## Термины

- **GTD-тик** — глобальный проход `runDue` (сейчас 5 мин): legacy-записи `gtd/*.json`
  (чек-листы) **и** durable-шаги в одном проходе.
- **Тик ожиданий** — новый лёгкий интервал (~30 с), который опрашивает **только**
  ждущие durable-шаги детерминированными валидаторами, без LLM и без запуска чек-листов.
- **Wake** — `task_item_wake` → `woken_at` в `wait_json` (шаг обязан проснуться сейчас, а не на следующем тике).
- **Kick** — `kickDurable()` (`src/gtd-controller.js:1837`, дебаунс 3 с,
  `runDurableSerialized`) либо `POST /internal/gtd/tick` (`src/handlers/internal.js:99`)
  для процессов вне сервера.

## Не-цели (сознательно НЕ делаем)

- **Не ускоряем чек-листовый GTD-тик** — legacy `gtd/*.json`, кроны, ETA-доводка и
  `FIRE_LEASE_MS` остаются на 5 минутах. Плоскость меняется только для ожиданий durable-шагов.
- **Не трогаем первый тик после старта** (2 мин) — он про чек-листы, не про ожидания.
- **Не строим свой event-bus вместо GitHub webhook** — событийный CI либо уже есть, либо уходит в follow-up issue.
- **Не добавляем LLM в опрос** ожиданий (инвариант спеки: опрос только детерминированный).
- **Не делаем drain / «рестарт запланирован» / рассылок** — рестарт остаётся мгновенным и тихим.
- **Не поднимаем второй процесс сервера** для опроса (ловушка: дублирует pending-tasks).

## Крайние случаи

- **Ждущих шагов нет** → тик ожиданий дешёвый no-op: сначала счётчик
  (`wait_json IS NOT NULL AND resolved IS NULL`), при нуле — выход без запросов.
- **Спам пробуждений** (пользователь пишет подряд, условие мигает) → дебаунс 3 с +
  сериализация; лишний wake = «пересмотреть сейчас», попытка не тратится (DW-01).
- **Wake по невыполненному условию** → шаг снова уходит в `waiting`, блокировка
  следующих шагов сохраняется.
- **Rate limit GitHub API**: один ждущий `ci_green` при 30 с ≈ 120 запросов/час
  (лимит токена 5000/час — запас есть). Если ждущих шагов станет много — общий
  интервал/backoff, это называется вслух, не прячется.
- **Проснувшийся шаг и очередь слотов** (#1752): он стартует только в свободный
  слот, как и сейчас, — ускорение пробуждения не увеличивает параллелизм.
- **Пустой/битый `until`** → уже отклоняется сразу (неизвестный валидатор), поведение сохранить.
