# Core 02 — Видимость фоновых запусков

Issue #1729 · эпик #1726 (единый контракт запуска, вопрос 5 «как пользователь узнаёт о результате и о сбое»).
Статус документа: **сценарии согласованы владельцем 28.09.2026** (решения в конце документа). Код пишется по этим ID.

## Зачем

Пользователь должен в любой момент понимать три вещи:

1. **Что это за работа.** Каждое сообщение, которое бот прислал не в ответ на только что отправленную реплику, говорит, к какой задаче оно относится.
2. **Началась ли она.** Если работа ушла в фон, пользователь видит момент, когда она реально стартовала, а не только «план ведёт исполнитель».
3. **Чем кончилась.** Успех, сбой или «нужен человек» приходят всегда. Молчание не бывает исходом.

Пользователь принял второе сообщение за результат кнопки. Это ожидаемо: в сообщении нет ни слова о том, чья это работа. Отсюда три дыры:

- **Д1. Нет ярлыка.** Фоновые сообщения не подписаны.
- **Д2. Нет ack старта и сигнала сбоя.** Для планов, кронов и отложенных запусков. Хуки уведомлений по умолчанию выключены.
- **Д3. GTD продолжает чужую задачу.** Корневой `checklist.md` не имеет владельца, и доводка цепляется к любой следующей сессии проекта.

## Термины

- **Фоновый запуск**: любой запуск, который начался не как прямой ответ на только что отправленное сообщение или тап. Сюда входят GTD-доводка, шаг durable-плана, крон, отложенный запуск (timer/event), резюм после рестарта.
- **Интерактивный запуск**: ответ на сообщение или тап. У него уже есть видимый прогресс: сообщение «🧠 …» с таймером и кнопкой «⛔ Стоп» (`claude-runner.js`), а для тапа ещё и «▶️ <label>…».
- **Ярлык работы (run label)**: короткое имя задачи, 3–8 слов, до 60 символов, по-русски, без эмодзи. Пример: «PR по #1721: кнопки на ожидании», «История группы в тихом режиме».
- **Источник**: иконка в шапке. 🔁 доводка (GTD), 📋 план, ⏰ крон/таймер, ♻️ резюм после рестарта.
- **Статус-сообщение запуска**: одно сообщение на фоновый запуск. Его редактируют по мере хода работы, итог приходит ответом (reply) на него.

## Правила формулировок

- Шапка всегда первой строкой, ярлык всегда в «ёлочках».
- Не больше одной строки о том, «что дальше». Никаких внутренних id в тексте, кроме номеров PR и issue.
- При сбое причина пишется человеческими словами («не указан репозиторий»), а не `DURABLE: waiting without task_item_wait`.

## Как это ляжет в код (эскиз, уточним после согласования)

- Одна точка `runNotice(run, kind)`, где `kind ∈ {start, progress, fail, needs_human, done}`. Её зовут все источники вместо своих `sendT`. Это и есть канал «сбой → пользователю» из #1726.
- `run.label` и `run.statusMessageId` хранятся в durable-записи запуска: у плана в durable-task-store, у GTD в gtd-записи, у крона в записи крона.
- У чек-листа появляется владелец: строка `Owner-session: <id>` в шапке `checklist.md`. Её пишет тот, кто создаёт чек-лист (`cicd_track_pr`, агент). Legacy-чек-лист без владельца к новой сессии не цепляется.

### BV-08 / BV-08a: как сделано (PR #1730)

- **Формат.** Владелец — строка `Owner-session: <sessionId>` внутри секции `Goal:` (сразу под ней). Отмена — строка `Cancelled: YYYY-MM-DD` там же. Обе относятся к **активной** секции (последней с пунктами, как и раньше в `readChecklist`). Отменённая секция остаётся активной и считается закрытой: старые секции журнала не воскрешаются. `readChecklist` теперь отдаёт `owner` и `cancelled`.
- **Кто пишет строку владельца.**
  1. Агент. В DEEP-блоке промпта (`answer-router.js`) и в GTD-промпте доводки (`buildReopenMessage`) есть инструкция подписывать новую секцию. Id сессии движок получает в `AGENT_SESSION_ID` (env рана, в allowlist изоляции). В GTD-промпт id подставлен явно.
  2. Раннер, фолбэк. После рана `scheduleGtdAfterRun` → `claimFreshChecklist` подписывает активную секцию сессией рана, если выполнены все условия: у секции нет владельца, `checklist.md` менялся не раньше старта рана (`initiatedAt`), её не ведёт чужая открытая GTD-запись, и она не числилась осиротевшей до старта. Так тулы, которые строку не пишут (например, `cicd_track_pr` из engineering-skills), не ломают дефолт «создал PR → чек-лист → GTD». Сам `cicd_track_pr` живёт в другом репо и пока строку не пишет.
  3. «▶️ Делать» переподписывает секцию на сессию, которая её доводит.
- **`scheduleFromChecklist({sessionId: A})`.** Сессия A получает доводку, если владелец секции = A. Legacy-секция без владельца цепляется, только если у A уже есть открытая GTD-запись по этому `projectDir`. Отменённая секция не цепляется никогда. Остальная дедупликация (активный durable-план, один трекер на `projectDir`, один на чат) не изменилась.
- **Осиротевшая секция** (`src/orphan-checklists.js`, `isOrphan`). Все условия сразу: в секции есть открытые пункты и она не отменена; никакая открытая GTD-запись профиля не ведёт этот `projectDir`; при этом владельца нет, **или** у владельца нет открытой GTD-записи и его сессия сейчас не бежит (`isSessionRunning`). Признак проверяется заново перед отправкой напоминания.
- **Store.** Файл `<workDir профиля>/gtd-orphans.json`. Он лежит не в `gtd/`: `listGtd` читает там каждый `*.json` как GTD-запись. Ключ записи — `sha1(projectDir + goal)[:12]`, этот же id уходит в `callback_data`. Поля: `firstSeenAt`, `remindedAt`, `remindedHash`, `cancelledAt`, `doneAt`, `doingAt`, `label` (цель, обрезанная по слову до 60 символов), `chatId`, `threadId`, `username`, `audience`, `projectDir`, `openHash`, `openCount`, `firstOpen`. Запись появляется, когда ран пропускает осиротевшую секцию, или при `/all_forgotten_checklists`. Чат для напоминания берётся из чата сессии-владельца, если она жива, иначе из чата, где секцию заметили.
- **Напоминание.** Шлёт существующий GTD-тик (`_runDueInner` → `remindDue`), новых таймеров нет. Отправка идёт через `_tgNotify` с `chatId`/`threadId`, текст `🔁 «<ярлык>»: остался пункт «…»[ и ещё N]`, кнопки `ocl|do|<id>` / `ocl|no|<id>`. Условия: прошло не меньше 30 мин от `max(firstSeenAt, mtime checklist.md)`; не более одного раза на `(секция, хэш открытых пунктов)`; не чаще раза в 24 ч на секцию. `remindedAt` пишется до отправки, поэтому краш дубля не даёт. Показ в `/all_forgotten_checklists` засчитывается как напоминание.
- **Кнопки.** Обработчик — `POST /internal/orphan-checklists/action` (Bearer `AGENT_SECRET`, без LLM). Тело: `{username, action: do|no, id, chatId, threadId}`, ответ: `{ok, status, text}`. Шлюз правит сообщение на `text` и убирает кнопки.
  - «Делать» пишет GTD-запись (`source: 'orphan-checklist'`, `dueAt = now`, `label`). Запись привязана к сессии-владельцу, если та существует, иначе к новой сессии. Новая сессия создаётся без `chatId`, поэтому указатель текущей сессии чата не сдвигается. Затем роут сразу дёргает тик. Если тик уже в полёте, запуск подхватит следующий, это не дольше 5 мин.
  - «Отменить» ставит `cancelledAt` и дописывает `Cancelled:` в секцию. `checklist.md` не удаляется. Если доводка была запущена кнопкой «Делать», она тоже закрывается.
- **`/all_forgotten_checklists`** (алиас `/all_forgotten_checlists`) обрабатывается детерминированно в `_runTaskInner` (`FORGOTTEN_CHECKLISTS_INTENT`). Сканируются папки всех проектов профиля (`projects.listProjects`) и корень профиля. Бот отвечает сообщением-заголовком и отдельным сообщением с кнопками на каждую запись, максимум 10. Если записей нет, приходит «Забытых чек-листов нет». В шлюзе команда добавлена в `commands-registry.json` (`handler: forward`).
- Тесты: `test/gtd-checklist-owner.test.cjs`, `test/orphan-checklist-reminder.test.cjs`, `tests/runner-e2e.test.js` (`/all_forgotten_checklists`), `test/gtd-schedule-hook.test.cjs` (фолбэк-подпись и legacy).
