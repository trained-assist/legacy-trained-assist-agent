# Core 02 — Видимость фоновых запусков

Issue #1729 · эпик #1726 (единый контракт запуска, вопрос 5 «как пользователь узнаёт о результате и о сбое»).
Статус документа: **сценарии согласованы владельцем 28.09.2026** (решения в конце документа). Код пишется по этим ID.

## Зачем

Пользователь должен в любой момент понимать три вещи:

1. **Что это за работа.** Каждое сообщение, которое бот прислал не в ответ на только что отправленную реплику, говорит, к какой задаче оно относится.
2. **Началась ли она.** Если работа ушла в фон, пользователь видит момент, когда она реально стартовала, а не только «план ведёт исполнитель».
3. **Чем кончилась.** Успех, сбой или «нужен человек» приходят всегда. Молчание не бывает исходом.

Пользователь принял второе сообщение за результат кнопки. Это ожидаемо: в сообщении нет ни слова о том, чья это работа. Отсюда три дыры:

- **Д1. Нет ярлыка.** Фоновые сообщения не подписаны.
- **Д2. Нет ack старта и сигнала сбоя.** Для планов, кронов и отложенных запусков. Хуки уведомлений по умолчанию выключены.
- **Д3. GTD продолжает чужую задачу.** Корневой `checklist.md` не имеет владельца, и доводка цепляется к любой следующей сессии проекта.

## Термины

- **Фоновый запуск**: любой запуск, который начался не как прямой ответ на только что отправленное сообщение или тап. Сюда входят GTD-доводка, шаг durable-плана, крон, отложенный запуск (timer/event), резюм после рестарта.
- **Интерактивный запуск**: ответ на сообщение или тап. У него уже есть видимый прогресс: сообщение «🧠 …» с таймером и кнопкой «⛔ Стоп» (`claude-runner.js`), а для тапа ещё и «▶️ <label>…».
- **Ярлык работы (run label)**: короткое имя задачи, 3–8 слов, до 60 символов, по-русски, без эмодзи. Пример: «PR по #1721: кнопки на ожидании», «История группы в тихом режиме».
- **Источник**: иконка в шапке. 🔁 доводка (GTD), 📋 план, ⏰ крон/таймер, ♻️ резюм после рестарта.
- **Статус-сообщение запуска**: одно сообщение на фоновый запуск. Его редактируют по мере хода работы, итог приходит ответом (reply) на него.

## Правила формулировок

- Шапка всегда первой строкой, ярлык всегда в «ёлочках».
- Не больше одной строки о том, «что дальше». Никаких внутренних id в тексте, кроме номеров PR и issue.
- При сбое причина пишется человеческими словами («не указан репозиторий»), а не `DURABLE: waiting without task_item_wait`.

## Как это ляжет в код (эскиз, уточним после согласования)

- Одна точка `runNotice(run, kind)`, где `kind ∈ {start, progress, fail, needs_human, done}`. Её зовут все источники вместо своих `sendT`. Это и есть канал «сбой → пользователю» из #1726.
- `run.label` и `run.statusMessageId` хранятся в durable-записи запуска: у плана в durable-task-store, у GTD в gtd-записи, у крона в записи крона.
- У чек-листа появляется владелец: строка `Owner-session: <id>` в шапке `checklist.md`. Её пишет тот, кто создаёт чек-лист (`cicd_track_pr`, агент). Legacy-чек-лист без владельца к новой сессии не цепляется.
