# Core 05 — Долговечность web-сессии: id живой в момент выдачи

Issue #1867 · PR: trained-assist-agent#1873 (squash `6295409`, в проде 29.09.2026 12:30 МСК).
Статус документа: **сценарии подтверждены живой проверкой в проде 29.09.2026** (создание сессии → `/web/session-get` 200 → `/web/reply-bearer` отвечает; после деплоя 0 вхождений «session not found» в логе).

## Зачем

Веб отдаёт пользователю ссылку на сессию (id `s-web-<ts>-<rand>`) в момент её создания: браузер получает событие `session` и работает с этим id дальше. Если в окне «id выдан → прогон стартовал» агент перезапускался (или прогон не материализовался: отказ admission, ошибка старта), ссылка оставалась фантомом — открытие и ответ давали 404 «session not found», при создании — «Подтверждение не получено».

Инцидент-источник: репорт владельца 29.09.2026 10:14 МСК, профиль mbk_luda_recruiter, сессия `s-web-1790665749936-6de89430` (открытие → 404, файла на диске нет).

Инвариант: **любой id, отданный клиенту в событии `session`/`done`, обязан читаться с диска в момент выдачи и после рестарта.** Невыполнимый инвариант → видимая retryable-ошибка, а не тихий фантом.

## Термины

- **Момент выдачи (mint)**: `streamWebTask` (`src/web-routes.js`) минтит id и шлёт клиенту событие `session`. Теперь до этой отправки создаётся **durable-шелл**: файл сессии с 0 сообщений + запись в индекс (`createSession({pending})` в `src/session-store.js`); `buildContext` для пустого шелла возвращает null — нет ложного «Продолжение …».
- **Точный web-id (`webExactSession`)**: флаг веб-прогона; быстрый ответ (pre-queue, `/usage` и т.п.) и utility-команды внутри рана пишут обмен в тот же `s-web-…` id, что отдан клиенту, а не в побочную `qa-<hash>` сессию.
- **Фантом**: id, отданный клиенту, чей файл на диске отсутствует → все обращения к нему отвечают 404 «session not found».

## Не-цели (сознательно не делаем)

- Telegram-путь не меняется: все правки под флагом `webExactSession`.
- Схемы данных, квитанции web-воркера и воркер trained-assist-web не трогаются.
- «Выдавать id только после записи» как отдельная механика не строится — ломает Stop/навигацию; вместо этого запись сдвинута раньше выдачи.

## Крайние случаи

- **Рестарт между выдачей id и стартом рана** → сессия существует (шелл), повторный ответ продолжает её, а не даёт 404.
- **Быстрый ответ до постановки в очередь** → обмен записан в точный id, ссылка из браузера работает.
- **Пустой шелл в контексте** → `buildContext` возвращает null: нет ложной пометки «Продолжение».
- **`done` без файла на диске** → явная ошибка (WS-04), фантом невозможен.
