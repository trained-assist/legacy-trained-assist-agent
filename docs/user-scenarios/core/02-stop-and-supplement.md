# Core 02 — «⛔ Стоп» и «➕ Дополнить» на идущей задаче

Статус: **спецификация, кода нет**. Этот PR фиксирует целевое поведение, риски и
тест-план. Реализация будет в следующих PR, и каждый будет ссылаться на ID ниже.
Затрагивает два репозитория: `trained-assist-agent` (runner, GTD, durable) и
`trained-assist-tg-bot` (callbacks, intake buffer, outbox, retry queue).

## 0. Инцидент и почему это класс, а не единичный баг

28.09.2026 12:40–12:45 МСК, чат владельца, задача в Call Tips:

1. Нажал «⛔ Стоп» → бот ответил «остановлено». Результата нет. Через несколько
   секунд задача снова работает («перерождается»).
2. Нажал «➕ Дополнить» → «✏️ Напиши текст следующим сообщением — остановлю текущую
   задачу и перезапущу с ним как с дополнением». Отправил текст. Дальше ничего:
   кнопки подтверждения нет, задача не перезапущена, дополнение не применено.
   Перед этим голосовое во время задачи дало «✓ Получил ещё 4 сообщений, пока идёт
   задача. ▶️ Запустить агента», а «▶️» — «⏳ Идёт текущая задача…». Как видно из
   §1.1, текст дополнения попал в тот же держатель.
3. «📜 Журнал» → «Лог процесса недоступен для этой сессии».

Это уже не первая правка этого сценария. Каждый раз чинили один путь и не
проверяли сквозной. Поэтому здесь сначала контракт на всё поведение, потом код.

## 1. Как это работает сейчас (факты из кода, main на 28.09)

### 1.1 «Дополнить» не может сработать в проде (детерминированный баг)

- `tg-bot src/handlers/callbacks.js:818-831`: `sup|` записывает в KV-сессию
  `pendingSupplementDraft {taskId, sessionId, expiresAt=+10мин}` и шлёт «✏️ Напиши
  текст…».
- Следующее текстовое сообщение приходит в `routeText` (`src/index.js:348`).
  Там `shouldDebounce()` возвращает true для любого текста при включённом `INTAKE`
  (дефолт в проде). Сообщение уходит в intake buffer (`/ingest`), и
  `handleMessage` не вызывается. **`routeText` вообще не смотрит на
  `pendingSupplementDraft`.**
- Проверка черновика есть только в `handleMessage` (`src/handlers/message.js:117`) и
  стоит под `!msg.intakeItems`. Когда буфер позже отдаёт пачку, `intakeItems`
  выставлен, и ветка снова пропускается.
- Итог: дополнение оседает в «держателе» как обычное сообщение. Показывается
  «Получил ещё N сообщений», `supok|` не появляется никогда, черновик тихо
  истекает через 10 минут.
- Почему тесты зелёные: `tests/supplement-running-task.test.js` вызывает
  `handleMessage` напрямую, без `env.INTAKE`. Тест обходит тот самый роутер, в
  котором и сидит баг.

### 1.2 «Стоп» убивает только то, что в эту секунду является живым процессом

- `stopok|` (`callbacks.js:797-805`) вызывает `POST /tasks/stop {username, chatId,
  audience, threadId}`. taskId из кнопки выбрасывается. Шлюз верит полю
  `killed` и ничего не перепроверяет.
- Агент (`server.js:920`, `runner/index.js:351`): обходит `activeTimers`,
  **пропускает записи без `s.proc`**, ставит `userStopped=true` и шлёт один
  `SIGTERM` прямому ребёнку. Ребёнок при изоляции — это `sudo … <engine>`. Группа
  процессов не убивается, до SIGKILL не доходит, ответ не ждёт выхода процесса.
  Ответ всегда `200 ok`, даже при `killed:0`.
- Пути, которые Стоп не видит и которые перезапускают задачу:
  | # | Путь | Почему выживает |
  |---|---|---|
  | R1 | Retry backoff (`retry-policy.js`, 30с/3м/10м через `setTimeout`) | во время ожидания в `activeTimers` нет процесса, `killed:0`; таймер потом стреляет без проверки стопа |
  | R2 | Хоп продолжения/ретрая, стоящий в `admission.run` | `consumePendingStop` наполняет только web (`stopSessionTask`); кнопка TG его не трогает |
  | R3 | GTD (`gtd-controller.js:1497`, `_runDueInner`) | пропускает только `isTaskRunning`; ответ «⛔ Остановлено» не распознаётся как терминальный, и запись заново ставится в `dueAt`. Набранное текстом «стоп» зовёт `clearGtdForChat`, а кнопка — нет |
  | R4 | Durable-исполнитель (`settleDurableReply`) | остановленный ответ без DURABLE-маркера считается провалом, и `recoverDurableItem` делает ретрай; `USER_STOP` существует в `recovery-policy.js`, но его никто не выставляет |
  | R5 | `timedOut` проверяется раньше `userStopped` (`runner/index.js:2146`) | Стоп после 38-минутного SIGTERM или inactivity-kill превращается в автопродолжение (до 10 раз) |
  | R6 | Шлюз: `launchAfterRelease` в intake buffer, RunOutbox alarm, `processDueRetries` | Стоп не чистит ни буфер, ни outbox, ни retry queue; после «освобождения» они запускают новый ран |
- Частичный результат («⛔ Остановлено» + последний ход, `appendReply
  "[остановлено пользователем]"`, `CANCELLED`) пишется **только если процесс
  реально вышел**. Если SIGTERM не дошёл (sudo/подпроцессы) или Стоп попал в
  R1/R2, ничего не сохраняется. Это и есть «не сохраняет никакого результата».

### Ключевое архитектурное решение (одно, без меню)

> **Ревизия при реализации — см. §2а.** Цель и все ID ниже не меняются; заменён
> только механизм адресации: вместо наследуемого `taskChainId` — выводимый
> `traceId` (адрес диалога) + timestamp-гейт `initiatedAt <= stoppedAt`.
> Ответственность GTD/durable за свой гейт (R3/R4) зафиксирована там же.

**Стоп адресует цепочку задачи (`taskChainId`), а не pid и не «юзера целиком».**
- `taskChainId` выдаётся на первом `runTask` и наследуется всеми ретраями,
  продолжениями, GTD-итерациями и durable-хопами.
- Стоп пишет durable-тумбстоун `stopped:{taskChainId}` на диск агента: переживает
  рестарт, TTL 24ч. Каждая точка перезапуска (retry fire, admission start,
  continuation, GTD `_runDueInner`, durable recover, `resumePendingTasks`) проверяет
  тумбстоун перед спавном. Точек перезапуска несколько, и завтра появится новая.
  Одна проверка «на входе в спавн» закрывает класс, а не пять конкретных путей.
- Кнопки несут короткий ключ цепочки. Агент хранит маппинг `controlKey → taskChainId`,
  так что хеш `h…` перестаёт быть «ничего не значащим».
- Процесс движка спавнится в своей группе процессов (`detached` / `setsid`, для
  sudo-изоляции — kill через slot-пользователя). Стоп = SIGTERM группе → 5с → SIGKILL
  группе → подтверждение выхода.
- Supplement становится **серверной операцией** `POST /tasks/supplement
  {taskChainId, text, files}`: агент атомарно делает стоп, дожидается подтверждения
  и стартует новый ран в той же сессии. Сейчас шлюз делает `stopTask().catch(()=>{})`
  + `runTask` в обход буфера, и это гонка by design.

### 2а. Ревизия реализации: traceId + timestamp-гейт вместо реестра цепочек

Реализация (PR «Стоп: kill дерева + trace-тумбстоун») сохраняет ВСЕ ID выше
(SS-01…SS-13, R1…R6, K1…K15) и все инварианты §2 (TTL 24ч, fail-open,
переживает рестарт, одна проверка на входе в спавн), но заменяет **механизм
адресации**:

| | §2 (taskChainId) | §2а (реализация) |
|---|---|---|
| Ключ | `taskChainId`, выдаётся на первом `runTask` и наследуется хопами | **traceId** — адрес диалога, ВЫВОДИТСЯ из координат: для TG `conversationKey` (тот же ключ, что и admission-lane: bot+chat+topic), для web `профиль+сессия` |
| Проверка | хоп сверяет свой `taskChainId` с тумбстоуном | `!fromUser && initiatedAt <= stoppedAt(trace)` |
| K1 (новая задача не блокируется) | новый запрос = новая цепочка | **структурно**: `POST /run` и web-ран помечены `fromUser` и проходят всегда; у внутреннего хопа `initiatedAt` (момент исходного запроса юзера) старше отметки Стопа |
| K14 (переживает рестарт) | тумбстоун на диске + проверка в `resumePendingTasks` | то же: `stopped-traces/*.json` на диске; resume наследует `initiatedAt` из журнала `pending-tasks` и гейтится |

Почему не `taskChainId`: поля нет ни в кнопках (шлюз шлёт в `/tasks/stop` только
`{username}`), ни в `pending-task-record`, ни в чём ещё — пришлось бы добавить
и прокидывать его через 6 хопов и журнал. Адрес диалога уже есть и уже
сериализуется admission-ом: одна линия `traceIdFor()` даёт тот же эффект, что и
наследуемый chainId, без нового состояния. `initiatedAt` при этом **уже**
наследуется всеми 6 хопами и резюмом — переносить пришлось ничего.

Что от этого меняется практически:

- **Точка проверки — две, а не одна:** до `savePendingTask` (ловит retry после
  backoff'а, resume после рестарта) и внутри `admission.run` (ловит хоп,
  стоявший в очереди, когда пришёл Стоп — R2). Обе читают один и тот же
  тумбстоун; вторая дешёвая, т.к. файл читается только если trace вообще
  останавливался.
- **Координаты для Стопа, пришедшего без chatId:** шлюз шлёт `{username}`, а
  тумбстоуну нужен адрес. Реестр живых ранов (`liveRuns`, синхронная запись в
  `runTask`, снятие на settle внешнего промиса — спанет retry-backoff) плюс
  журнал `pending-tasks` дают координаты ранов без процесса. Это закрывает R1/R2
  без единого нового состояния в журнале.
- **GTD и durable не полагаются на `initiatedAt`** (они его не передают, гейт их
  не поймает): R3 закрывается пре-проверкой `stoppedAt >= rec.createdAt` перед
  fire + `closedReason: 'user-stop'` в `.then()`/`settleResumedGtd`; R4 —
  `settleDurableReply` помечает `USER_STOP` терминально и не доходит до
  `recoverDurableItem`.
- **`taskChainId` остаётся запланированным для SS-11** (кнопки адресуют цепочку,
  а не «что сейчас бежит») — это отдельная задача на боке шлюза, а не на агенте.

## 3. Риски — где можно облажаться

| # | Риск | Как закрываем |
|---|---|---|
| K1 | Тумбстоун слишком широкий → блокирует новую задачу, которую юзер запустил после Стопа | ключ = trace-адрес диалога, а не chat/user «вообще»; `POST /run`/web-ран помечены `fromUser` и проходят всегда (§2а); тест SS-01 «новая задача после стопа запускается» |
| K2 | Тумбстоун слишком узкий → какой-то путь перезапуска обходит проверку | `initiatedAt` наследуется всеми хопами, а гейт стоит в двух точках спавна и читает один тумбстоун (§2а); ревью: любой новый spawn-путь обязан пройти через общий `isRunStopped` |
| K3 | Kill группы процессов под sudo-изоляцией: у агента нет прав слать сигнал процессам slot-пользователя | kill через тот же `sudo -n -u slot kill -- -PGID` (sudoers уже разрешает запуск от slot) или через `setsid` + pidfile; смоук на реальной изоляции, не на моке |
| K4 | Убиваем чужое: общий workDir профиля, параллельные чаты, web + TG, разные боты | только по trace-адресу диалога (§2а) + правило владельца #1303; регресс-тесты CH-02/CH-04/CH-06 + `task-stop-ownership` остаются зелёными |
| K5 | Перехват «следующего сообщения» для Дополнения съест обычное сообщение (юзер нажал и забыл) | окно 10 мин + явное подтверждение (`supok`) до любого действия; ↩️ возвращает текст в обычный поток (в держатель), а не выбрасывает |
| K6 | Гонка: задача завершилась между `sup` и `supok` | SS-08: агент отвечает `already_finished`, шлюз запускает дополнение как продолжение сессии; ровно один ран |
| K7 | Двойной запуск после supplement: буфер держал сообщения + `launchAfterRelease` + новый ран | supplement-ран регистрируется в буфере как `busy` (сейчас идёт в обход); держатель после Стопа не автозапускается (SS-05) |
| K8 | Частичный результат пустой или врёт (скретч-нарратив, «сейчас сделаю…») | используем тот же `pickFinalText`, что и для таймаута; если связного хода нет — «остановлено до результата», без фантазии |
| K9 | Durable/playbook: `USER_STOP` делает шаг терминальным, план застревает навсегда | шаг → `cancelled_by_user`, план показывает «остановлен пользователем, ▶️ продолжить» — явное возобновление, не автоматическое |

## 4. Как тестируем

**Правило для всех тестов ниже:** вход через реальную точку (webhook → `routeText`
с `env.INTAKE`; HTTP `/tasks/stop`, `/tasks/supplement`), движок = fake engine с
латчами (как в core-admission), наблюдаем процессы и спавны, без sleep-угадайки и
без LLM-судьи.

1. Запустить долгую задачу (`sleep 600` через bash-тул) → «⛔ Стоп» → «Точно» →
   в течение 10с «⛔ Остановлено. Что успел: …»; `ps` на хосте — нет процессов
   движка этого slot; 5 минут тишины (переживает цикл GTD).
2. Снова долгая задача → «➕ Дополнить» → текст → кнопка подтверждения ≤3с →

   ровно одно прогресс-сообщение.
3. «📜 Журнал» → ссылка открывает журнал той же сессии.
4. `/health` шлюза и агента → SHA = merge-коммит main.
