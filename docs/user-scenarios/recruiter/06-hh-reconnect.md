# Recruiter — Переподключение HH после истечения токена

**Домен:** HeadHunter рекрутинг — управление авторизацией  
**Суть:** HH OAuth токен протухает через 2 недели. Нужен graceful reconnect без потери state.  
**Критичность:** Высокая — если это сломано, рекрутер теряет доступ ко всему

---

## Контекст (начальный state)

- HH подключён, но токен истёк (expires_in прошёл)
- Активная вакансия: сохранена в context store
- ATS-критерии: сохранены
- История кандидатов: на диске

---

## Сценарий A — Обнаружение истёкшего токена

### A1 — Любой запрос к HH

```
User: покажи отклики
```

**Ожидаем:**
- Бот получает 401 от HH API
- Не падает, не показывает стектрейс
- Понятное сообщение: "Доступ к HeadHunter истёк. Нужно переавторизоваться."
- Даёт ссылку на авторизацию

**Validation:**
- Сообщение не содержит `401`, `Unauthorized`, `token expired` в сыром виде
- Содержит OAuth-ссылку

---

### A2 — После переавторизации

*OAuth прошёл, новый токен записан*

```
User: теперь работает?
```

**Ожидаем:**
- Бот проверяет токен (GET /me или GET /vacancies/mine)
- "Подключение восстановлено"
- State не потерян: активная вакансия та же, критерии те же

**Validation:**
- `contexts/hh/active_vacancy.json` не изменился
- `ats_criteria.json` не изменился
- История кандидатов на месте

---

## Сценарий B — Refresh токена

*Если HH выдал refresh_token вместе с access_token*

### B1 — Автообновление в фоне

```
User: покажи топ кандидатов
```

**Ожидаем:**
- Бот видит что access_token близок к истечению (или уже истёк)
- Автоматически использует refresh_token для получения нового access_token
- Сохраняет новый токен
- Запрос выполняется прозрачно для пользователя

**Validation:**
- Пользователь не видит запроса на переавторизацию
- Новый токен записан в `~/agent-tokens/{username}/hh`
- refresh_token обновлён тоже (HH ротирует их)
- То же в фоне: `hh_sync_messages` сам обновляет просроченный токен через refresh_token, без переподключения. Для этого серверу инструментов нужны HH_CLIENT_ID/HH_CLIENT_SECRET — они приходят из секретов сервера (issue #1892, см. `core/06-tool-platform-keys.md`); в логе нет «HH OAuth client credentials are not configured»
- Переподключение нужно только если HH отклонил refresh (сценарий B2)

---

### B2 — Refresh тоже протух

```
User: покажи отклики
```

*Refresh_token тоже истёк (>30 дней неактивности)*

**Ожидаем:**
- Бот понимает что refresh не прошёл (400/401 от token endpoint)
- Переходит в режим полной переавторизации (как в сценарии A)
- Не зависает в цикле попыток

---

## Сценарий C — Отключение HH

```
User: отключи headhunter
```

**Ожидаем:**
- Бот удаляет `~/agent-tokens/{username}/hh`
- Подтверждает: "HH отключён. История кандидатов сохранена."
- State не трогает (можно заново подключить и продолжить работу)

**Validation:**
- `~/agent-tokens/{username}/hh` — файл удалён
- `contexts/hh/` — НЕ удалён (история остаётся)

---

### C1 — Переподключение после отключения

```
User: подключи headhunter снова
```

**Ожидаем:**
- OAuth flow заново
- После подключения: активная вакансия и критерии восстановлены из context store

---

## Edge Cases

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Токен истёк посередине длинной задачи | Прерывает задачу, сообщает о 401, не частично исполняет |
| OAuth callback не пришёл (пользователь не завершил) | После таймаута: "Авторизация не завершена. Попробуйте ещё раз" |
| Старый токен + попытка отправить сообщение | 401 перехватывается до отправки, сообщение не потеряно |
| HH заблокировал приложение | Понятное сообщение про блокировку, не "401" |

---

## Проверяемые инварианты

1. 401 от HH никогда не приводит к потере state (context store нетронут)
2. После успешного reconnect — первый запрос не требует повторного ввода команды
3. Токен хранится с `mode 0o600` — не world-readable
4. refresh_token обновляется при каждом использовании (HH требует ротацию)
