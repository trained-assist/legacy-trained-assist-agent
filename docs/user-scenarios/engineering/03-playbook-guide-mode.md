# Engineering — Режим «гайд» плейбука: шаги как чек-лист в живом диалоге

**Домен:** плейбуки (эпик #1887, п.1 — режим «гайд»)
**Профиль:** любой профиль, запускающий плейбук для мелкой задачи или задачи «давай обсудим»
**Тулы:** `playbook_run({playbook_id, goal, mode:"guide"})` (`src/mcp-skills/tools/102-playbooks.js`),
компилятор `src/playbook-compiler.js`, `checklist.md` проекта, системный промпт агента (правило выбора режима)
**Базовый сценарий:** `01-development-playbook.md` (фоновый durable-путь) — гайд описывает альтернативный режим того же плейбука
**Охват:** только п.1 #1887. п.2 (вопрос всплывает в чат-владелец для фоновых планов, после #1886)
и п.3 (флаг `interactive: true` у шага) — отдельные срезы, здесь НЕ входят.

## Ценность

**Одна фраза:** пользователь, которому нужно пройти плейбук для мелкой или обсуждаемой задачи,
получает шаги как **живой чек-лист в текущем диалоге** и двигает его с агентом пошагово — без
молчащего фонового плана и без шагов, висящих «в ожидании ответа»; объективные гейты (CI/staging)
остаются обязательными.

**Доказанность: V4.** Источники:
- Владелец в голосе 2026-09-29 (issue #1887): «сейчас плейбук = фоновый план, который уходит в фон и
  молчит… нет режима обсуждения», «шаг паркуется в „ждём ответа“ (blocked by user), а вопрос появляется
  как служебная вставка в чужих сессиях». Требование записано в requirements-log **[140]**.
- Обходной путь уже реально используется: прогресс плейбуков ведётся **руками в `checklist.md` проекта**
  (текст #1887 — «как делается руками сейчас»); профиль PO ведёт так планы на ежедневной основе
  (напр. этот самый эпик, скриншоты в рабочих папках планов). То есть пользователь уже «платит» руками за
  то, что гайд-режим даст автоматически.

## Контекст (начальный state)

- Пользователь в **живой сессии** бота (Telegram или web) — текущий диалог с агентом.
- Плейбук сохранён и виден через резолв (profile → sibling → system), напр. `development` или профильный.
- Активного durable-плана по этой цели нет (или пользователь сознательно идёт в гайд).
- Действует правило выбора режима (системный промпт): «делай» + ясная задача → фон (как сейчас);
  «давай обсудим»/есть вопросы/мелочь → гайд. Фоновый режим по умолчанию не меняется.

## Сценарий

| # | Актор → блок | КОГДА … ТОГДА … |
|---|---|---|
| 1 | Юзер в живой сессии: мелкая/обсуждаемая задача («давай обсудим, как правильнее поставить багфикс X», «сделай мелочь Y, но пройдём по шагам в диалоге») | КОГДА задача попадает под правило «мелочь / давай обсудим» ТОГДА агент вызывает `playbook_run({playbook_id, goal, mode:"guide"})` — без `activate` |
| 2 | То же, противоположный случай | КОГДА юзер говорит «делай» + ясная задача ТОГДА агент вызывает `playbook_run` БЕЗ `mode` — фоновый durable-план, поведение ровно как сегодня (регрессия недопустима) |
| 3 | Компилятор + `playbook_run(mode:"guide")` | КОГДА передан `mode:"guide"` ТОГДА НЕ создаётся запись в durable-хранилище (`durable_tasks`) и НЕ плодится скрытая фоновая сессия `s-plan-<id>`; возвращаются отрендеренные шаги как чек-лист (заголовки, проверки, гейты) для исполнения в текущей сессии |
| 4 | Агент → окружение сессии | КОГДА чек-лист получен ТОГДА агент открывает прогресс в `checklist.md` проекта текущей сессии (как сегодня ведётся руками) и ставит первый шаг в работу прямо в диалоге |
| 5 | Шаг, которому нужен ввод юзера | КОГДА очередной шаг требует ответа пользователя ТОГДА вопрос задаётся **обычным сообщением в той же живой сессии**; шаг НЕ паркуется в «ждёт ответа»/blocked-by-user и не всплывает грязной вставкой в других сессиях |
| 6 | Юзер отвечает на вопрос | КОГДА юзер отвечает в этом же диалоге ТОГДА агент принимает ответ и продолжает выполнение следующего шага чек-листа |
| 7 | Гейты CI/staging | КОГДА в чек-листе есть шаг-гейт (CI зелёный, staging на актуальной версии) ТОГДА гейт обязателен и не пропускается — тот же критерий, что в фоновом плане: красный гейт не закрывает шаг, агент сообщает и доводит до зелёного |
| 8 | Прогресс по ходу | КОГДА шаг выполнен ТОГДА статус в `checklist.md` проекта обновлён; при перерыве сессии работа восстанавливается по этому файлу (как при текущем ручном ведении) |
| 9 | Завершение | КОГДА все шаги чек-листа закрыты (гейты зелёные, приёмка на проде) ТОГДА агент даёт итог в диалоге; durable-плана не существует — это разовый живой диалог с чек-листом |

## Не-цели (этого среза)

- **Не** меняем фоновый режим по умолчанию: `playbook_run` без `mode` создаёт durable-план как сегодня.
- **Не** реализуем п.2 #1887 (всплытие вопроса в чат-владелец для фоновых планов) — блокер #1886, отдельный PR.
- **Не** реализуем п.3 #1887 (флаг `interactive: true` у шага, исполнение в живой сессии по завершении фона).
- **Не** добавляем автоматическую эскалацию «гайд → фон»: если пользователь ушёл, продолжение — по `checklist.md` руками, без фонового исполнителя.
- **Не** вводим новые проверки/валидаторы и не трогаем системные гейты плейбуков.

## Крайние случаи

- **Пользователь ушёл посреди гайда.** План не «зависает» и ничего не размораживается GTD: незакрытые шаги остаются в `checklist.md` проекта, в новой сессии агент может продолжить по нему вручную — это и есть текущее ручное поведение.
- **Тот же плейбук уже крутится в фоне.** Гайд — отдельная сущность, конфликта нет, но агент предупреждает о дубле цели, чтобы не получить два параллельных исполнения.
- **Красный гейт (CI/staging).** Как в фоне: шаг не закрывается, агент докладывает и доводит до зелёного; пропуск/continue-on-error в гайде так же недопустим.
- **Плейбук не сохранён / не виден.** Та же ошибка, что в фоне (`PLAYBOOK_NOT_FOUND`) — гайд не обходит резолв.
- **Дурацкая цель / пустой goal.** Валидация компайлера та же, что для фонового запуска: `goal` обязателен.
- **Рестарт VM.** Живая сессия гайда умирает, но прогресс переживает в `checklist.md`; «сам всплыть» диалог не сможет — это уже п.2 / #1886.

## Validation (что проверяет прод-смоук и тесты)

- На сценарии web-canary: `playbook_run(..., mode:"guide")` возвращает шаги чек-листом и НЕ создаёт durable-задачу (пустой список планов до/после).
- Шаг 7: гейт из чек-листа нельзя пометить выполненным при красном CI (тот же детерминированный валидатор).
- Регрессия: `playbook_run` без `mode` создаёт durable-план, как до фичи.

## Риски и открытые вопросы (не блокируют работу)

- **Куда пишется прогресс гайда:** в проект текущей сессии (`checklist.md` проекта). При отсутствии проекта — решить на шаге реализации (рекомендация: корень cwd, как пишутся ручные чек-листы сегодня).
- **Цена:** шаги гайда исполняет живая модель напрямую — для больших плейбуков дороже фонового пула дешёвых моделей; гайд позиционируется на мелочь/обсуждение, риск зафиксирован в эпике (лимиты на вызов — на этапе реализации, если понадобится).
- **Кто пишет прогресс:** в гайде нет durable-исполнителя и авто-проекции GTD, поэтому статус в `checklist.md` обновляет сам агент живой сессии. Это тот же механизм, что ручное ведение сегодня; синхронизация с дурабельной проекцией не нужна — её тут нет.
