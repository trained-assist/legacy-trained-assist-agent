# Engineering — Личный плейбук: собрать без выдуманных проверок и найти из обычной просьбы

**Домен:** конструктор кастомных плейбуков (эпик #1851, срезы S4a + S4b; база — #1372 P1)
**Профиль:** любой профиль, который собирает личные плейбуки (`~/users/<p>/playbooks/*.json`)
**Тулы:** `playbook_draft` / `playbook_edit` / `playbook_save` (`src/playbook-authoring.js`),
`playbook_check_reachability` (`src/playbook-reachability.js`), реестр проверок `src/playbook-validators.js`,
системный промпт профиля (runner)

## Ценность

1. **S4a (D1):** владелец профиля, описав процесс словами («проверить фичу на проде»), получает
   плейбук, в котором каждая программная проверка реально исполняется ядром — ни одной выдуманной
   проверки, которую молча «решает» LLM-судья, и ни одного литерала `{var}` в цели плана.
   Негативная форма: сохранить плейбук с несуществующей программной проверкой **не получилось**.
2. **S4b (D2):** владелец профиля пишет обычную просьбу («проверь, доехала ли фича») — агент сам
   предлагает/запускает его личный плейбук, не требуя помнить id.

**Доказанность: V3.** Источник — владелец продукта на живом примере 2026-09-29 (комментарий
#1851#issuecomment-5883779762): `playbook_draft` выдал 13 шагов с `shell_command_success` /
`http_ok_contains_sha` (нет в реестре), programmatic-шаги с «выполните curl…», `{scenario}` без
`inputs[]`; `playbook_check_reachability` для `prod-feature-check` и `logs-investigate` — `dispatch: fail`.
Обходной путь уже используется (V5-признак): маршрут вписан руками в правила проекта PO.

## Шаги (S4a — сборка плейбука)

| # | Актор → блок | КОГДА … ТОГДА … |
|---|---|---|
| 1 | Юзер в чате: «сделай плейбук: проверить фичу на проде» → агент вызывает MCP `playbook_draft(description)` | КОГДА вызван draft ТОГДА Hermes получает в промпте (`AUTHORING_PROMPT`) **реестр программных проверок** (ключи из `createDefaultRegistry()` с однострочным описанием) и **каталог типовых шагов** (`library/step-types.json`: id — назначение), и правило «programmatic = только ключи реестра, без инструкций к исполнению» |
| 2 | Hermes → черновик | КОГДА Hermes вернул JSON ТОГДА `validatePlaybook` + новая проверка: в каждом `execution_kind: "programmatic"` шаге все ключи `validation` ∈ реестр; иначе черновик уходит на repair-круг с текстом ошибки (`unknown programmatic validator "<key>" в шаге <id>; доступны: …`) |
| 3 | То же | КОГДА `goal_template` содержит `{name}` (кроме `{input}`), а `inputs[]` не объявляет `name` ТОГДА та же ошибка валидации (`{name} в goal_template без inputs[]`) → repair |
| 4 | То же | КОГДА Hermes заполнил `when_to_use` (1–2 фразы «когда предлагать», на языке юзера) ТОГДА черновик проходит; пустое/отсутствующее `when_to_use` у `scope: profile` → repair |
| 5 | Агент → юзеру: сводка черновика | КОГДА draft прошёл ТОГДА юзер видит шаги, реальные проверки и строку «когда использовать» |
| 6 | Юзер «сохрани» → `playbook_save(id)` | КОГДА save ТОГДА те же проверки повторяются (защита от ручной правки черновика); при нарушении — `ok:false` с конкретным ключом/переменной, файл профиля не пишется |
| 7 | Юзер «поправь: …» → `playbook_edit` | КОГДА edit ТОГДА промпт тот же (реестр + каталог), валидация та же; `when_to_use` сохраняется/обновляется |

## Шаги (S4b — достижимость)

| # | Актор → блок | КОГДА … ТОГДА … |
|---|---|---|
| 8 | Любая новая сессия профиля → runner собирает системный промпт | КОГДА у профиля есть `playbooks/*.json` с `when_to_use` ТОГДА в промпт добавлен блок «Твои плейбуки: `<id>` — <when_to_use> → `playbook_run(playbook_id: "<id>")`» (коротко, с лимитом на кол-во/длину) |
| 9 | Юзер: «проверь, доехала ли фича X и работает ли» | КОГДА просьба совпадает по смыслу с `when_to_use` ТОГДА агент вызывает/предлагает `playbook_run("prod-feature-check")` без упоминания id юзером |
| 10 | Владелец/CI → `playbook_check_reachability(id)` | КОГДА профильный плейбук имеет непустой `when_to_use` ТОГДА `dispatch: pass` (новый маршрут «P профильный блок промпта»); без `when_to_use` — `dispatch: fail` с подсказкой «заполни when_to_use» |

## Не-цели
- Runtime-разворачивание `{use: "<step-type>"}` в профильном плейбуке (это S4, отдельный срез); здесь каталог step-types только **показывается** Hermes как словарь.
- Новые валидаторы (`shell_command_success` и т.п.) — не добавляем; программная проверка исполнения команд — отдельное решение (безопасность).
- Блоки `qa_user_send` / `prod_status` / `logs_*` (S1–S3), lifecycle/архив (S5).
- Системные плейбуки: их маршрутизация (prompt-domains A1) не меняется.

## Крайние случаи
- Существующие профильные плейбуки без `when_to_use`: читаются и запускаются как раньше (поле опционально для чтения/запуска, обязательно для нового draft/save); в промпт не попадают; health подсказывает заполнить.
- `validation` programmatic-шага с ключом, который есть в реестре, но значение неверного типа — не блокируем здесь (поведение как сейчас).
- Много плейбуков у профиля — блок промпта ограничен (≈10 шт., `when_to_use` обрезается до ~160 символов) с явной пометкой «ещё N, см. playbook_list», не молча.
- Hermes повторно выдумывает ключ после repair — draft возвращает ошибку юзеру (не сохраняет мусор).
- `{input}` остаётся разрешённой переменной без `inputs[]`.
- Реестр пополнится новыми ключами — промпт строится из реестра динамически, не хардкодом.

## Как проверяем (приёмка)
- Юнит: validatePlaybook/draft-валидация отклоняет unknown programmatic key и `{var}` без `inputs[]`; принимает реестровые ключи и `{input}`.
- Юнит: runner-блок промпта содержит `id — when_to_use` для профиля с плейбуком; пуст без плейбуков.
- Юнит: `playbook_check_reachability` профильного плейбука с `when_to_use` → dispatch pass; без → fail.
- Прод: `playbook_draft` «проверить фичу на проде» — все programmatic-ключи из реестра; `playbook_check_reachability prod-feature-check` (после заполнения `when_to_use`) → dispatch pass.
