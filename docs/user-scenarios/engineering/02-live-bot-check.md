# Engineering 02 — Проверка живого бота из сессии (блоки prod_status / qa_user_send / qa_trace)

Эпик #1851, срез S1. Статус: сценарий зафиксирован 29.09.2026 (план 11f2f462, шаг define-use-case). Код пишется по этим ID.

## Ценность

Агент-инженер (и владелец, который его нанял) **за один-три вызова инструментов получает доказательство, что фича работает на живом боте**: какой релиз крутится, что бот ответил тестовому юзеру, какие кнопки показал и что при этом случилось внутри. Без поиска эндпоинтов, секретов и путей логов заново в каждой сессии.

Негативная ценность (безопасность): **реальный клиент не получил ни одного сообщения от проверки**, а агент в слоте не получил ни одного секрета сервера.

Доказанность: **V3**, источник — запрос владельца 2026-09-29 (эпик #1851, раздел «Зачем»), плюс наблюдаемый обходной путь: агенты каждый раз вручную ищут `/web/run-bearer`, `AGENT_SECRET` и journal (ad-hoc тест-профили web-canary, webqa, iso-smoke, 64 профиля mt* — след этого обходного пути). Близко к V5 (обходным путём пользуются сейчас), но пользователь один — владелец.

## Акторы

- **Агент-исполнитель** — сессия любого профиля (в т.ч. в слоте ta-agent-N без доступа к localhost:8080 и без секретов). Вызывает MCP-инструменты.
- **Сервер агента** (assist-agent, :8080) — исполняет инструменты от своего имени, держит секреты.
- **Тест-профиль** `qa-<profile>` — «юзер», от имени которого пишется боту.
- **Владелец** — читает вердикт в Telegram.

## Шаги (плейбук prod-feature-check, первые три блока)

| ID | Шаг | Функциональный блок | Ожидаемое поведение (EARS) |
| --- | --- | --- | --- |
| LB-01 | Агент проверяет, доехал ли релиз | MCP `prod_status(expect_sha?, journal_minutes?=15)` | КОГДА вызван без аргументов ТОГДА возвращает `{agent:{commit, uptimeSec}, gateway:{buildSha}, journalErrors:{count, sample[≤5]}}`. КОГДА передан `expect_sha` ТОГДА добавляет `agent.contains_expected` / `gateway.contains_expected` (true, если expect_sha — предок развёрнутого коммита, через merge-base в git-источнике), а при false — `verdict:"not-deployed"` |
| LB-02 | Агент пишет боту от имени тест-юзера | MCP `qa_user_send(text, session_id?)` → сервер: `/web/run-bearer` (новая сессия) или `/web/reply-bearer` (продолжение) | КОГДА вызван без `session_id` ТОГДА сервер от имени `qa-<caller>` запускает реальный ран и возвращает `{sessionId, reply, buttons:[{label, callback}], durationMs, status:"done"}`. КОГДА передан `session_id` ТОГДА продолжает ту же сессию того же тест-профиля |
| LB-03 | Агент смотрит, как система отреагировала | MCP `qa_trace(session_id, limit?)` | КОГДА вызван ТОГДА возвращает сжатый след: `messages[]` (role, text ≤500 симв.), `journal[]` (строки с этим sid, время в МСК, ≤50), `executions[]` (execution-history по sid: tools, длительность, исход). Время в ответе всегда МСК, исходная UTC-метка сохраняется в поле `utc` |
| LB-04 | Агент выносит вердикт | Текст агента по данным LB-01…03 | КОГДА commit содержит мерж, в ответе есть ожидаемое и в journal нет ошибок по sid ТОГДА PASS с тремя доказательствами; иначе FAIL с указанием блока |
| LB-05 | Проверка из живой сессии (приёмка S1) | Любая прод-сессия профиля PO | КОГДА из прод-сессии вызваны LB-01→LB-02→LB-03 ТОГДА получены коммит прода, текст ответа бота и его след — без ssh, curl и секретов в сессии |

## Безопасность и лимиты

| ID | Правило | Проверка |
| --- | --- | --- |
| LB-S1 | `qa_user_*` работает ТОЛЬКО с тест-профилем вызывающего `qa-<caller>` (создаётся автоматически при первом вызове, один на профиль) или с профилем из серверного allowlist. Имя целевого профиля агент не передаёт | Unit: попытка указать чужой username → отказ `QA_PROFILE_FORBIDDEN`; реальный профиль недостижим ни одним аргументом |
| LB-S2 | Секреты (`WEB_VERIFY_SECRET`/`AGENT_SECRET`) не попадают ни в аргументы, ни в ответ, ни в env сессии | Unit: ответы инструментов не содержат значения секрета; вызов идёт серверной стороной |
| LB-S3 | Слот ta-agent-N не видит localhost:8080 — инструмент всё равно работает | Исполнение внутри процесса сервера (или через публичный URL с per-session токеном), не из слота |
| LB-S4 | Лимит: ≤20 `qa_user_send` в час на профиль и ≤1 одновременный ран на тест-профиль | Превышение → `QA_RATE_LIMITED` с `retryAfterSec`, ран не стартует |
| LB-S5 | Тест-профиль не шлёт ничего в Telegram (канал web) | У `qa-*` нет chatId; исходящие в TG отсутствуют |
| LB-S6 | `qa_trace` отдаёт след только сессий тест-профилей вызывающего | Чужой/реальный sid → `QA_SESSION_FORBIDDEN` |

## Крайние случаи

- Бот не ответил за таймаут (по умолчанию 180 с) → `status:"timeout"`, `sessionId` всё равно возвращается, чтобы вызвать `qa_trace`.
- Ран упал → `status:"error"` + последняя ошибка; не исключение инструмента.
- `session_id` не существует или чужой → `404 session not found` / `QA_SESSION_FORBIDDEN`.
- Шлюз `/health` недоступен → `gateway:{error}`, агентная часть возвращается (частичный результат, не провал).
- `expect_sha` неизвестен в git-источнике → `contains_expected:null` + `reason:"unknown sha"` (а не false).
- Повтор того же вызова (сетевой ретрай) → идемпотентность через `requestId`, дубль-ран не стартует (409 → вернуть существующий sessionId).
- Journal в UTC, интерфейс в МСК — конвертация на сервере, не в агенте.

## Не-цели (S1)

- Нажатие кнопок (`qa_user_press`) — срез S3.
- Карта логов и произвольные запросы к логам (`logs_map`/`logs_query`) — срез S2.
- Отправка через Telegram-канал в реальный чат — отдельный срез.
- Уборка ad-hoc тест-профилей mt* и прочих — срез S6 (необратимо, с апрувом).
- Проверка от имени реальных клиентов — никогда.

## Открытые вопросы (помечены как риск, не блокируют)

Решается на шаге дизайна (архитектурная развилка), дефолт — per-session токен, выданный сервером при старте сессии.
