# 2026-10-01 — Песочница событийного пробуждения durable-плана (эпик #1846, план `16eac5da`)

Шаг «Песочница» плана `16eac5da`: исполняемая форма сценария
`docs/user-scenarios/core/05-durable-wait-events.md` (EV-01…EV-12). Фичи ещё нет —
песочница **красная по делу**, это её рабочее состояние до срезов S1–S5.
Полный дизайн — issue [#1846](https://github.com/trained-assist/trained-assist-agent/issues/1846).

## Запуск

```
npm run sandbox:durable-wait-events     # цикл ~0.5 с, уровень S3, детерминированный вывод
```

Текущее состояние: `0/12 PASS`, каждая проверка красная с указанием, чего не хватает.
Цикл зелёный на эталонной реализации (проверено, откачено) — контракты достижимы.

## Контракты, которые пинит песочница

1. **Каталог событий — в реестре `createDefaultRegistry`,** пять ключей:
   `issue_pr_merged`, `issue_pr_ci_green`, `workflow_run_completed`,
   `workflow_run_green`, `workflow_job_completed`. Ключ, зарегистрированный «вхолостую»,
   не считается: EV-01 зовёт каждый на правдоподобном субъекте и требует вердикт
   (`pass`/`fail`/`inconclusive`), а не исключение. Регистрация в реестре — единственное,
   что нужно `task_item_wait`, чтобы принять `until` (он сверяется с
   `Object.keys(getDefaultRegistry())`), поэтому новые типы подхватываются без правок
   в `durable-wait.js`.
2. **Обработчик вебхука — экспортируемая функция `(req, url, res, ctx) → true`,** `false`
   значит «не мой маршрут». Ищется **по возможности, а не по имени** (8 кандидатов
   вроде `src/handlers/github-webhook.js`): песочница пинит контракт, а не имя файла.
3. **Fail-closed порядок:** 404 (секрет не настроен) → 413 (тело велико) → 401
   (подпись неверна, тело даже не разбирается) → 400 (не-JSON) → 202. Любой отказ
   **не трогает ни шаг, ни durable-тик** — подпись сверяется timing-safe **по сырому телу
   до** `JSON.parse`.
4. **Секрет вебхука** — из `secrets`; песочница кладёт фикстуру во все известные имена
   (`GITHUB_WEBHOOK_SECRET`, `GH_WEBHOOK_SECRET`, `DURABLE_WEBHOOK_SECRET`,
   `WEBHOOK_SECRET`, `GITHUB_WEBHOOKS_SECRET`) в ctx и env, иначе проверки «404 без
   секрета» и «202 с секретом» неразличимы.
5. **Вебхук только будит:** `due_at = now` у совпавшего waiting-шага + кик
   (`durable-kick.notify` / `gtd.kickDurable`). Вердикт — всегда проверщик из реестра
   (EV-08 проверяет все три исхода: `satisfied` / шаг ждёт дальше / `failed`).
6. **Матчер — по типу события и субъекту:** `owner/repo#N`,
   `owner/repo/actions/runs/<id>`. Чужое репо, чужой номер, PR без мера не будят наш шаг.
7. **Маршрут — до глобального Bearer-гейта `src/server.js`** (как `/health`): GitHub шлёт
   только HMAC, Bearer не пришлёт. nginx `location /agent/` уже пробрасывает (проверено,
   правок не требует).

## Решения песочницы

- **S3, а не S5/S4.** Реальные функциональные блоки (SQLite-store, тик ожиданий, MCP-тул,
  реестр, поверхность вебхука), фейк только у GitHub API у проверщиков, время инжектится.
  Полный `src/server.js` **не поднимается** — он резюмирует чужие задачи (видел дубль
  задачи при локальном запуске). Поэтому поведение вебхука проверяется вызовом его
  обработчика напрямую, а **монтаж** в `server.js` — структурно по исходнику. S4 (прод-смоук
  «секунды») остаётся приёмкой на деплое.
- **Кик-шпион через `durable-kick.useInProcess`** — тот же seam, что и у реального MCP-тула,
  поэтому «будильник сработал» измеряется без подмены внутренностей.
- **Секрет для подписи отделён от секрета агента** (`signSecret` vs `secret`): иначе
  «подпись чужим секретом» неотличима от «агент настроен на этот секрет».

## Что песочница поймала на эталонной реализации

Прогон сначала-red-против-реализации — обязательный порядок: песочница, которая красная
всегда, не проверяет ничего. На первой эталонной реализации нашлось 5 расхождений, из
которых **четыре были дефектами самой песочницы** (свойство проверок, а не кода):

- **Красный прогон ДОЛЖЕН будить `*_green`-ожидание.** Реализация будила
  `workflow_run_green` только при `conclusion: 'success'` — и «финальный провал» из сценария
  (B.2) не срабатывал бы **никогда**: красный CI не разбудил бы шаг, тот спал до
  `deadline_at`. Матчер обязан публиковать `*_green`-субъект на **любом** `completed`,
  независимо от вывода: решение — за проверщиком (`fail` + `evidence.final`).
  Это главная грабли эпика, и она поймана песочницей, а не ревью.
- **Проверка «не тронут» на постороннем (но валидном) событии** была чрезмерно строгой:
  требовала ноль киков. Инвариант — «ни один шаг не взведён»; тик без совпадений безвреден.
  Строгость оставлена только там, где она про безопасность: неаутентифицированный запрос не
  должен дотягиваться до бизнес-логики вообще (EV-04).
- **Запасной путь (EV-09) проверялся некорректно:** подписка брала дефолтный опрос 300 с,
  шаг не был «пора» — тик его и не claim'нул. Теперь подписка с `poll_every_sec: 30`, а тик
  приходит в `due_at + 1 мс`: ровно так он ходит в бою.
- **EV-11 искал литеральный путь** `/webhooks/github` в `server.js`, а монтаж ссылается на
  модуль (путь живёт внутри). Ищем признак монтирования, а не строку.
- **HMAC-кейс был неотличим от «секрет настроен на этот ключ»** (см. выше).

## Грабли песочницы (окружение)

- **В свежем воркспейсе нет `node_modules`** → `MODULE_NOT_FOUND: better-sqlite3`. Ставится
  `NODE_ENV= npm install` (`NODE_ENV=production` блокирует установку — известная ловушка).
- `NODE_ENV=` в окружении пуст, ставить можно обычным `npm install`; шум в
  `package-lock.json` (`"peer": true`) откатывается — песочница не добавляет зависимостей.
- Песочница **обязана** подменять `AGENT_DATA_DIR` + `USERS_DIR` (как у соседней
  `durable-wait-latency`): иначе тесты писали бы в боевой `~/agent-data`.
